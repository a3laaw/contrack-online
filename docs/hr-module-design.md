## 1) الفلسفة: الموظف الموحد — نمدّد ما هو قائم لا نكرره

- ConTrack يملك **فعلًا** كيان `employees` مبسطًا (اسم/هاتف/ملاحظات/نشط) يخدم نظام **السلف** (PV/CV/SD) والرُقب.
- **قرار بنائي**: موديول HR يوسّع هذا الكيان نفسه بإضافة الحقول المهنية — لا كيان ثانٍ. هكذا:
  - نظام السلف الحالي يعمل كما هو بلا أي ترحيل بيانات.
  - نفس روح NovaFlow («السجل الموحد للقوى العاملة») وروح «الموظف الموحد» عندهم.
  - نتجنب فجوة G2 (كيانان لنفس المعنى).
- **التباعد عن NovaFlow المتعمد**: لا ننسخ `departments`/`jobs` كجدولين في HR-1 — القسم والمسمى حقولا نصية (لا مرجعيات لبقية النظام بعد، فلا خطر G7). التسوية المعرفية تُدرس في HR-3 عند ربط التكلفة.
- «HR لا يعرف المشاريع، لكن المشاريع تعرف HR» — المسير بلا أي `contractId`. (النسب للتقدير لاحقًا في HR-3 بالتجميد اللحظي Cost Snapping.)

## 3) المخطط (Prisma) — كيانات HR-1

### 3.1 توسعة `Employee` (الجدول القائم `employees` — بلا ترحيل)
```prisma
model Employee {
  // القائم: companyId id name phone notes active vouchers
  // الجديد:
  jobNumber    String @default("") @map("job_number")   // يبدأ من 1001 — توليد آلي بذر عدم
  employeeType String @default("internal") @map("employee_type") // internal | external (خارجي يحرر إلزامية الراتب الشهري)
  department   String @default("")
  jobTitle     String @default("") @map("job_title")
  civilId      String @default("") @map("civil_id")      // 10 أرقام — تحقق نواة
  nationality  String @default("")
  hireDate     String @default("") @map("hire_date")     // YYYY-MM-DD
  salary       Decimal @default(0)                        // الأساسي الشهري
  paymentBasis String @default("monthly") @map("payment_basis") // monthly | daily
  dailyRate    Decimal @default(0) @map("daily_rate")     // لأساس الأجر اليومي
  paymentMethodId Int? @map("payment_method_id")          // مرجع معرفي (G7) — طرق الدفع القائمة
  // annualLeaveBalance عمدًا غير مخزّن — دالة recount نقية (G9 من اليوم الأول)
}
```

### 3.2 جداول جديدة (كلها بcompany_id + تُضاف إلى TENANT_MODELS **فورًا** — درس T111 حاسم)
```prisma
model EmployeeAttendance {   // الحضور اليدوي اليومي
  employeeId Int, workDate String // YYYY-MM-DD
  status String // present | absent | justified_absent | leave | holiday
  checkIn String @default("")  // HH:MM — يُسجل ولا يُحتسب في مسير HR-1
  checkOut String @default("") @map("check_out")
  note String @default("")
  // unique(companyId, employeeId, workDate)
}

model EmployeeLeave {        // آلة الحالات — نمط EngineerLeave المجرَّب
  employeeId Int, leaveType String // سنوية | مرضية | طارئة | بدون راتب
  startDate String, endDate String, days Decimal // شاملة الطرفين — حساب آلي
  status String // pending | approved | commenced | returned | rejected
  decisionBy String @default(""), decisionAt DateTime?, decisionNote String @default("") // إلزامي عند الرفض
  sickTier Int? // شريحة المرضية القانونية (§4)
}

model PayrollBatch {         // مسير شهري
  month String // YYYY-MM — unique(companyId, month)
  status String // draft | approved | paid | cancelled
  grossTotal Decimal, deductionTotal Decimal, advanceTotal Decimal, netTotal Decimal
  journalEntryId Int? @map("journal_entry_id") // رابط مطلق بعد الاعتماد
  approvedBy/At, cancelledAt/reason, generatedBy/At
  records PayrollRecord[]
}

model PayrollRecord {        // سجل الموظف — لقطة مجمّدة (Cost Snapping)
  batchId Int, employeeId Int
  snapName String, snapJobTitle String, snapPaymentBasis String // لحظة التوليد — لا قراءة لاحقة
  baseAmount Decimal        // الشهري كاملًا أو dailyRate × أيام العمل
  absenceDeduction Decimal  // ∑ الغياب غير المبرر × (الأساسي/30) أو dailyRate
  advanceDeduction Decimal  // خطة خصم السلف (§6)
  netAmount Decimal
}
```

## 4) الإجازات: آلة الحالات + الامتثال الكويتي

- **الانتقالات**: `pending → approved → commenced → returned` (رفض من pending فقط بقرار موثق بنote إلزامي — نفس نمط EngineerLeave الناجح). لا حذف لمعتمد — إلغاء موثق.
- **الرصيد السنوي**: دالة نقية `recountAnnualLeave(hireDate, consumedApproved, policy)` —
  - السياسة: 30 يومًا/سنة (قانون العمل الكويتي 6/2010 م70) بنسبة استحقاق شهرية (2.5) بعد إتمام أول 9 أشهر خدمة — القيمة تُعرض دائمًا «محسوبة» لا مخزنة.
  - الاعتماد يستهلك من الرصيد — المرضية والطارئة لا تخصم من السنوية.
- **سلّم المرضية القانوني** (م66 — 6/2010): 15 يومًا بأجر كامل · 10 بـ75% · 10 بـ50% · 10 بـ25% · 30 بلا أجر — `sickTier` يُحسب آليًا من ∑ مرضية السنة، والأجر المتأثر يظهر كسطر خصم/نقص في المسير (HR-1: عرض وتحذير؛ الخصم الفعلي في التوليد للأجر الكامل فقط — تُثبّت الشرائح باختبار نواة قبل الإطلاق).

## 5) خط أنابيب HR→المالية (القلب — خط واحد)

```
حضور يدوي + إجازات معتمدة  →  توليد المسير (نواة نقية + لقطة مجمّدة)
  → مسودة batch (فحص: شهر غير مكرر، فترة مالية مفتوحة تُفحص عند الاعتماد)
  → اعتماد المدير (ذري): حراس ⇒ postJournalEntry (محرك موحد sourceType=payroll بتاريخ آخر الشهر)
  ⇒ القيد: مدين 5210 رواتب وأجور (الأساسي − خصم الغياب)
          دائن 2160 رواتب مستحقة (الصافي النقدي بعد خصم السلف)
          دائن حساب «سلف الموظفين» الأصل (advanceDeduction — يخفض ذمة الموظف)
  → الدفع: سند PV من 2160 (دفع جماعي للمسير أو فردي) ⇒ batch = paid
  → الإلغاء: قيد عكسي موثق عبر cancelJournalEntry — بلا حذف فيزيائي (نمط الزكاة)
```

- **دبابيس الحسابات**: 5210/2160 مبذوران فعلًا بالشجرة. حساب السلف الأصل يُقرأ من إعدادات السلف القائمة (يُثبَّت سلوكه باختبار اتصال قبل ربط النواة).
- **منع التكرار مع SD الحالي**: المسير يعرض خصم السلف معلوماتيًا مع رقم الحركة؛ سند SD اليدوي لموظف مشمول بمسير الشهر يظهر **تحذيرًا** (المنع الصارم تحسين HR-2).
- وضع الاعتماد (Task 112) ينسحب: الاعتماد للمدير حصرًا، غير المدير لا يولّد مسودة تُقيد أصلًا (التوليد نفسه محمي).

## 6) السلف: الاندماج لا الإعادة

- النظام القائم (spec-8-e) بجميع أنواعه (`advance/cash_return/deduction`) وواجهاته وAPIs **يبقى كما هو**.
- قسم «السلف» داخل تبويب HR = إطار يعرض نفس البيانات بسياق الموظف الموحد (رصيد الموظف بجانب ملفه) + زر خصم سريع يملأ المسير التالي.
- **لا يُلمس** voucher-server إلا لنقطة التحذير أعلاه.

## 7) الواجهة والشل والصلاحيات

- **الكتالوج**: `hr` · «الموارد البشرية» · أيقونة `users` (Users) — **إلزام إضافة الأيقونة لخرائط MODULE_ICONS وCATALOG_ICONS معًا** (درس consulting: بلا fallback) · `available:true` · `core:false` · `navModules:["hr"]`.
- **الشل**: تبويب «الموارد البشرية» رابعًا (بعد الاستشارات) ببنود section-based: `team / attendance / leaves / payroll / advances` (نمط الاستشارات). `navModulesFor` يخفيه لغير المفعّل.
- **HRView** (نمط ConsultingView): KPIs (نشطون · في إجازة الآن · حالة مسير الشهر · صافي المسير) · تبويبات حالة بكل قسم · بحث بتطبيع عربي · نوافذ إضافة/تعديل بـSearchableSelect (الموظفون/طرق الدفع) · شارات حالة المسير · توليد المسير بحوار تأكيد يعرض التجميعات · اعتماد/إلغاء بسببه · دفع جماعي.
- **الصلاحيات**: `screen_hr` (VIEW_PERMS · secretary:true — مفتاح ويب فقط) · الاعتماد والدفع للمدير (`isSuperRole` بالخادم) · `moduleGuard("hr")` على كل المسارات.
- **الموبايل**: 375px بلا تمرير أفقي، فوتر مثبت — كالعادة.

## 8) بذر الحسابات — تنقية موثقة على القرار 4

- آلية البذر التلقائي **تبقى** القرار المعتمد، لكن:
  - **HR-1 لا يبذر شيئًا**: 5210 و2160 موجودان في الشجرة أساسًا.
  - حسابات المخصصات (2161 مخصص إجازات · 2211 مخصص نهاية الخدمة) تُبذر آليًا **مع HR-2** لحظة بناء محرك المخصصات الذي يستخدمها فعلًا.
  - **السبب (درس G3/G5)**: «كل حساب يُستخدم أو لا يُبذر» — لا حسابات ميتة تضلل القوائم.

## 9) دروس NovaFlow المطبقة حرفيًا

| الدرس | التطبيق هنا |
|-------|-------------|
| G9 عدادات بلا recount | الرصيد السنوي دالة حسابية نقية من اليوم الأول + اختبارات |
| Cost Snapping (تجميد) | لقطة المسير `snap*` تُكتب عند التوليد ولا تُقرأ من ملف الموظف لاحقًا |
| G7 مرجعيات نصية | paymentMethod معرف · كل الروابط IDs · أي تعرفة مستقبلية بمعرف |
| G11 مطابقات نصية | الموديول بالمعرف `hr` عبر كتالوج — لا `includes('نص')` |
| G4/G6 مصدر وحيد | Prisma schema مصدر البنية الوحيد — بلا مخطط موازٍ |
| T111 (داخلي) | TENANT_MODELS تُحدَّث **بنفس الـcommit** — لا نافذة انكشاف |
| آلة حالات الإجازة | نفس الانتقالات الموثقة + قرار موثق بلا حذف فيزيائي |

## 10) خطة التنفيذ والاختبارات (بعد الاعتماد)

1. **السكيما**: توسعة Employee + 3 جداول جديدة + `db:push` + تحديث TENANT_MODELS/BACKUP_MODELS (ترتيب طوبولوجي).
2. **الكتالوج والشل**: الموديول + الأيقونات + التبويب + moduleGuard.
3. **النوى النقية**: `hr-core.ts` (recount الرصيد، آلة الحالات، حساب المسير والخصومات، شرائح المرضية) + `tests/hr-core.test.ts`.
4. **الخادم**: `hr-server.ts` + مسارات `api/hr/*` (team/attendance/leaves/payroll + توليد/اعتماد/إلغاء/دفع) مع audit بكل حركة.
5. **الواجهة**: HRView كاملة + ربط السلف.
6. **تحقق حي** (agent-browser بشركة بذر مؤقتة ثم تنظيف كامل): دورة كاملة موظف → حضور → إجازة معتمدة → مسير → قيد متزن → PV → paid → إلغاء موثق؛ وموبايل 375.
7. **البوابة والإعدادات**: بطاقة HR تظهر بالانضمام + لوحة المطور (تبديل/إيقاف — الإيقاف تجميد).

## 11) حدود HR-1 (ما لا يُبنى عمدًا)

- بلا استيراد Excel/بصمة (HR-2) · بلا أذونات تأخير/انصراف (HR-2) · بلا حاسبة نهاية خدمة (HR-2) ·
- بلا تكلفة عمالة على العقود ولا أطقم عمل (HR-3) · بلا قيود مخصصات (حساباتها تُبذر مع HR-2) ·
- بلا توظيف/applications (غير مطلوب) · المسير لا يلمس الزكاة أو iXBRL (شجرة القوائم القائمة تكفي كما هي).
