## المبدأ الحاكم (البنية المستهدفة)

```
                    ┌──────────────────────────────────────────┐
                    │           الأستاذ العام = مصدر الحقيقة     │
                    │   Account (شجرة واحدة) ← JournalEntry ← JournalLine │
                    └───────────────▲──────────────────────────┘
                                    │ قواعد ترحيل معلنة (PostingRule)
        ┌───────────────┬───────────┴────────────┬─────────────────┐
        │ السندات        │ الفواتير                │ المطالبات/البوابة │   ← مستندات تشغيلية
        │ Voucher        │ Invoice (بنود+سداد)     │ Claim / GatewayOp │
        └───────────────┴────────────────────────┴─────────────────┘
                 أبعاد تحليلية على سطر القيد:
                 customer | contract | subcontract | boqItem | project | costCenter | employee
```

1. **الأستاذ العام مصدر الحقيقة الوحيد**: لا يوجد أي رصيد مالي محسوب خارج `JournalLine` — لا رصيد في سند، ولا في فاتورة، ولا في شجرة مصروفات.
2. **شجرة واحدة**: `Account` هي الدليل الوحيد (موجودة من Task 102 بشجرة ذاتية + خريطة XBRL على كل ورقة + KWD ثلاثي). شجرة `ExpenseAccount` تُدمَج فيها ثم **تُسقَط** مع حقل الجسر `accountId`.
3. **المستند بلا قيد = مسودة**: كل سند/فاتورة مسجلة يولّد قيدًا متوازنًا إلزاميًا عبر قواعد ترحيل معلنة. الإلغاء = قيد عكسي مرتبط. لا حالات «مسجل بلا أثر محاسبي».
4. **العقود والمشاريع والباطن أبعادٌ لا أنظمة**: الجداول التشغيلية القوية (contracts/subcontracts/boq/projects) تبقى كما هي وتظهر في المحاسبة كأبعاد على سطر القيد — تُقرأ منها التقارير التحليلية، لا تُبنى منها أرصدة موازية.
5. **القوائم وXBRL تُشتق لا تُدخل**: كل قائمة مالية (القرار الوزاري 44/2016) تُبنى حصراً من الأستاذ عبر `xbrlElement` الموجود على الحسابات — ثم يُصدَّر iXBRL من نفس المصدر.
6. **KWD ثلاثي العشرة موحد**: `Decimal(18,3)` في كل جدول مالي جديد؛ تُجمَّع بالـSQL داخل المعاملات.

## جدول القرارات الهيكلية (من → إلى)

| الوضع الحالي | المشكلة الهيكلية | القرار |
|---|---|---|
| `JournalEntry` (debit/credit نصوص + مبلغ واحد) | ليس قيدًا مزدوجًا إطلاقًا | يُؤرشف ثم **يُستبدل**: رأس `JournalEntry` + أطراف `JournalLine` |
| `ExpenseAccount` (شجرة مصروفات تخلط عُهدًا وسلفًا kind=expense\|advance) | شجرة ثانية موازية بطبيعتين مختلطتين | تُرحَّل إلى `Account` (العُهد/السلف تصير أصولًا حقيقية) ثم **تُسقَط** مع الجسر |
| `Voucher.expenseAccountId` + `custodyAccountId` | مرجعان للشجرة القديمة | يُستبدلان بـ `accountId` واحد + `accountRole` في الدليل الموحد |
| `Voucher` المسجل بلا قيد | نظام نقدي موازٍ للأستاذ | يبقى مستندًا لكنه يولّد قيدًا إلزاميًا؛ السندات التاريخية (551) تُرحَّل تاريخيًا إلى قيود حقيقية |
| `Invoice` (رقم/عميل/مبلغ فقط) | بلا بنود ولا سداد ولا قيد | يُبنى من جديد: بنود + حالة سداد + قيد آلي؛ القديم يُرحَّل |
| شاشة «جسر المصروفات» (تبويب) | طبقة توصيل تعيش للأبد | تُحذف نهائيًا بعد الدمج |
| feature flags للتوازي | طبقات فوق طبقات | يُرفع علم `full_accounting` وتصبح المحاسبة هي النظام |
| عقود/باطن/BOQ/مراكز تكلفة | — سليمة | **لا تُمس**: تصير أبعادًا تحليلية على `JournalLine` |

ما **لا يُلمس**: بنية SaaS (Company/User/Permissions/AuditLog)، العقود ومراحلها وBOQ والملحقات والمطالبات والباطن التشغيلي، البوابة البنكية، النماذج المكتبية، النسخ والاستعادة.

## المرحلة 1 — النواة الصلبة (Tasks 104–106)

### Task 104 — نواة القيد المزدوج الحقيقية
- مخطط: `JournalEntry` الجديد (رأس): `entryNo` تسلسلي لكل شركة، `entryDate`، `description`، `status` (draft|posted|cancelled)، `sourceType`/`sourceId` (voucher|invoice|manual|migration)، `reversalOfId?`، `postedAt`/`postedBy`، `createdBy`.
- `JournalLine`: `entryId` FK، `accountId` FK للدليل، `debit`/`credit` Decimal(18,3) (مجذابة بطبقة money موحدة)، `description`، + أبعاد: `customerId?`، `contractId?`، `subContractId?`، `boqItemId?`، `projectId?`، `employeeId?`، `costCenter` — بلا FK على التشغيلي (قاعدة SaaS القائمة).
- `FiscalYear` + `FiscalPeriod` (open|closed) — تحكم التواريخ من اليوم الأول.
- النواة النقية `accounting-core.ts`: `validateEntry` (توازن Dr=Cr، لا سطر صفري، حساب ورقي مسموح نشره، تاريخ داخل فترة مفتوحة) + `postEntry`/`postReversal` داخل معاملة واحدة + قفل الحسابات النظامية غير المسموح نشرها.
- **أرشفة القيود النصية القديمة**: تصدير `journal_entries` الحالي إلى JSON محفوظ (نمط النسخ الاحتياطي) ثم ترحيل صفوفه إلى النموذج الجديد (كل سطر قديم = قيد من طرفين) بعلم sourceType=migration، ثم إعادة هيكلة الجدول.

### Task 105 — دمج الشجرتين (إسقاط ExpenseAccount نهائيًا)
- سكربت ترحيل: كل `ExpenseAccount` (الشجرة القديمة بأفرادها) → حساب في `Account` وفق الطبيعة الصحيحة: مصروف → 5xxx، عُهد وسلف → أصول 1xxx، تقدّمات عملاء → خصوم. مطابقة الاسم/المسار آلية + تقرير مراجعة لما لم يُطابق.
- استبدال المراجع: `Voucher.expenseAccountId`/`custodyAccountId` → `accountId` واحد (لا معنى لمرجعين لشجرتين بعد الدمج) + ترحيل `ExpenseAccount.accountId` الجسري للحفاظ على الربط الموجود، وتحديث مطالبات/تقارير تقرأ الشجرة القديمة.
- إسقاط `ExpenseAccount` + حقول snapshot الميتة + حذف تبويب «جسر المصروفات» ووحدة الجسر واختباراتها. `Account` تصبح الشجرة الوحيدة المتاحة للسندات والمستقبل.

### Task 106 — قواعد الترحيل + إعادة هيكلة السندات (القلب التشغيلي)
- `PostingRule`: قوالب قيود لكل نوع سند (قبض، صرف مصروف، صرف استحقاق عقد، صرف باطن، عهدة، إرجاع عهدة، خصم راتب، رسوم بوابة) — قابلة للضبط في إعدادات الشركة مع بذر افتراضي سليم.
- حفظ السند ⇒ توليد قيد posted متوازن إلزاميًا (من القاعدة): قبض ⇒ مدين نقد/بنك، دائن عميل؛ صرف مصروف ⇒ مدين مصروف الحساب المختار، دائن نقد/بنك/شيكات؛ عهدة ⇒ مدين عهد الموظف، دائن نقد/بنك… إلغاء السند ⇒ قيد عكسي مرتبط `reversalOfId`.
- **ترحيل تاريخي كامل للسندات (551)**: سكربت يولّد قيدًا لكل سند تاريخي (بأبعاده: عميل/عقد/باطن/مركز) + قيد افتتاحي موحد لأي فروق تعذر ربطها، ثم فحص توازن عام شامل (ميزان افتتاحي = ميزان ترحيل).
- شاشة السندات تعرض القيد المرتبط (رقم القيد + فتحه)، وقائمة «مسودات بلا قيد» تسقط من النظام (لا يوجد مسجل بلا قيد).

**معيار المرحلة 1**: ميزان المراجعة الداخلي متوازن Dr=Cr على كل الشركة، كل سند له قيد، شجرة واحدة فقط في النظام كله، صفر مراجع لـExpenseAccount في الكود.

## المرحلة 2 — الدورة المستندية (Task 107)

### Task 107 — الفواتير من الصفر (استبدال)
- `Invoice` جديد: `invoiceNo` تسلسلي، `customerId`، `contractId?`، تاريخ/استحقاق، `status` (unpaid|partial|paid|void)، إجماليات Decimal(18,3).
- `InvoiceItem`: وصف/كمية/سعر/خصم% — محصلة على الرأس تتحقق.
- قيد آلي عند الإصدار: مدين العميل (ذمم)، دائن إيراد العقود. السداد عبر السندات القائمة (`VoucherPaymentLink`) يحدّث حالة الفاتورة — مصدر سداد واحد لا ازدواج.
- ترحيل الفواتير القديمة للهيكل الجديد + أرشفة القديم. شاشة فواتير كاملة (فلاتر حالة، كشف عميل، طباعة PDF برأس الشركة).

## المرحلة 3 — مخرجات المحاسبة (Tasks 108–110)

### Task 108 — دفتر الأستاذ + ميزان المراجعة + الذمم
- دفتر أستاذ لأي حساب: حركات من القيود posted فقط + رصيد جارٍ، فلاتر (فترة/عميل/عقد/باطن/مركز)، تصدير CSV/Excel/PDF بالنمط الحالي.
- ميزان مراجعة حتى تاريخ: تجميع بالـSQL (لا JS)، توازن عام ظاهر، تجميع بالنوع والقسم.
- أعمار الذمم (30/60/90+) للعملاء والباطن من الجانب التحليلي لسطور القيد.

### Task 109 — الفترات والإقفال
- فتح/قفل فترة شهرية؛ المحرك يرفض أي قيد بتاريخ مقفل. قيد إغلاق سنوي للنتيجة إلى الأرباح المجمعة + افتتاحية السنة الجديدة. سجل إقفالات موثق.

### Task 110 — القوائم المالية (القرار الوزاري 44/2016)
- قائمة المركز المالي، قائمة الدخل الشامل، التغيرات في حقوق الملكية، التدفقات النقدية (تصنيف تشغيلي/استثماري/تمويلي عبر حقل `cashFlowKind` على Account).
- **تُبنى من GL عبر أقسام الدليل وxbrlElement حصرًا** — لا حسابات موازية ولا إدخال يدوي للأرقام. صفحة طباعة أنيقة + تصدير Excel، وتتطابق مع الميزان إلزاميًا (فحص توازن قبل الطباعة).

## المرحلة 4 — التوافق الكويتي (Task 111) ← الهدف الأساسي

### Task 111 — الزكاة + XBRL/iXBRL
- **الزكاة 1%** (قانون 8/2019 لصندوق الكويت الوطني): احتساب آلي من صافي الربح المستخرج من GL (بعد تعديلات النموذج المعلنة)، نموذج احتساب وإقرار سنوي بحالة (مسودة/نهائي) وقيد آلي للمخصص عند الاعتماد.
- **ضريبة دخل الأجانب 15%**: وحدة اختيارية تُفعَّل للشركات الأجنبية فقط (علم على الشركة) بنفس مصدر GL.
- **مصدّر XBRL/iXBRL**: توليد ملف التقديم (iXBRL بوسوم العناصر) من القوائم المالية عبر `xbrlElement` الموجود على كل ورقة — فحص اكتمال الخريطة قبل التصدير (تقرير «عناصر غير مغطاة») + معاينة داخلية قبل تنزيل الملف. البيانات الوصفية للشركة (الاسم/رقم الترخيص/السنة) من إعداداتها.

## قواعد التنفيذ الثابتة (لكل مهمة)
1. **نسخة احتياطية قبل أي ترحيل** + سكربت الترحيل مُختبر على نسخة أولًا، ذري داخل معاملة، والفشل = rollback كامل.
2. كل جدول جديد `companyId` من اليوم الأول عبر غلاف db القائم — لا استثناء.
3. لا feature flags للتوازي — الاستبدال مباشر مع أرشفة JSON قبل أي إسقاط.
4. معيار الجودة الموحد لكل Task: `bun test` أخضر + tsc/lint نظيفان + تحقق متصفح (1366/375) + worklog + رفع ببروتوكول PAT.
