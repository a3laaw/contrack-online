# تصميم «مراجعات المخططات + جسر الإنجاز إلى الفوترة» — البندان 1+2 من خريطة NOVA

> **المصدر:** بندا التأجيل (1) و(2) من docs/novaflow-study.md §9 بعد جسّ الواقع الحرفي للكود.
> **قرار الجسر الجوهري:** الفاتورة في ConTrack مستند مالي بقيد إصدار إلزامي — لا إنشاء آلي
> للفواتير إطلاقًا. الجسر = **اشتقاق «جاهز للمستخلص» + تجهيز بملء مسبق بضغطة** (نمط د9
> في الصيانة حرفيًا: اقتراح قابل للتنفيذ، لا مستند يتولد بذاته).

---

## 1) البند الأول — مراجعات المخطط (دورات V1→V2→V3)

### 1.1 النموذج `ConsultingRevision` (consulting_revisions)
| الحقل | النوع | الملاحظة |
|---|---|---|
| companyId / id | | فصل الشركات من اليوم الأول (درس T111) |
| contractId | Int → Contract Cascade | الدورة تنتمي لعقد (مشروع الاستشاري) |
| title | String | اسم المخطط/الوثيقة — مفتاح التجميع |
| revNo | Int | يُرقَّم خادميًا (max+1 لكل عقد+عنوان) — **بلا قيد فريد** (النص الحر لا يُحاصَر) |
| status | String | «بانتظار مراجعة» ⇐ (مقبول \| معاد بتعديلات) — آلة مغلقة G7، القرار نهائي |
| engineerId? | Int? → Engineer | مُعد الإصدار — اختياري |
| submittedAt / decidedAt / decidedBy / decisionNote | | decisionNote **إلزامي** عند الإرجاع (نمط إجازات المهندسين) |
| notes / createdBy / createdAt | | |

علاقات عكسية: `Contract.consultingRevisions` · `Engineer.revisions`.
فهارس: `@@index([contractId])` + `@@index([status])`.

### 1.2 النواة النقية `consulting-revision-core.ts`
`validateRevisionInput` (العنوان إلزامي، العقد/المهندس صحيحان) · `nextRevNo` (max+1 أو 1) ·
`canDecide/canEdit/canDelete` (القرار نهائي — لا تعديل ولا حذف بعد الحسم؛ الحذف للقيد المراجعة فقط) ·
`validateDecision` (الإرجاع بلا ملاحظة = خطأ) · `revisionKpis` (قيد المراجعة/مقبولة/معادة + دورات نشطة).

### 1.3 المسارات (تحت `screen_consulting` + `moduleGuard("consulting")` — نمط summary)
- `GET /api/consulting/revisions?contractId=` — القائمة مجمعة (عنوان ثم revNo تنازليًا) + ملخص
- `POST` — إنشاء دورة (revNo آلي + حدث عقد «مراجعة مخطط»)
- `PATCH /api/consulting/revisions/[id]` — تعديل قبل الحسم أو القرار (اعتماد/إرجاع)
- `DELETE` — قيد المراجعة فقط (405 عربي لغيره)

### 1.4 الواجهة
قسم خامس في الاستشارات `revisions` «مراجعات المخططات» (نمط الأقسام الحالية:
SECTION_META + SectionAction + نافذة إضافة + جدول مجمّع + أزرار قرار) + تبويب شل جديد.

## 2) البند الثاني — جسر الإنجاز إلى الفوترة (IPC مقترح)

### 2.1 الحالة الراهنة (اكتُشفت بالجسّ — لا تُعاد بناؤها)
إغلاق مرحلة ⇒ `triggerDuePayments` تفعّل سطور الخطة المرتبطة (`triggeredAt`) وتنشئ مطالبة
تلقائية — **موجودة وتعمل**. الناقص الوحيد: ربط «السطر المُثار» بفاتورته وإبراز الجاهزين.

### 2.2 التعديل البنيوي الوحيد
`Invoice += paymentId Int? → PaymentPlanItem` (+عكس `PaymentPlanItem.invoices` +فهرس).
الرابط يجعل الاشتقاق دقيقًا (لا تخمين نصي — درس G7) ويخدم تقارير لاحقة.

### 2.3 الاشتقاق `readyIpc` (نقي قابل للاختبار في contrack-core)
للعقد: سطور `triggeredAt≠""` و`remaining>EPS` ومرحلتها مغلقة وغير متخطاة، **بلا فاتورة
غير ملغاة** بنفس `paymentId` ⇒ قائمة { lineId, title, amount=remaining, stageName,
finishDate, dueDate }. إعادة فتح مرحلة تصفّر الترغيب (موجود) — وفاتورة صادرة تبقى (مستند مالي).

### 2.4 التكامل
1. `GET /api/contracts/[id]/overview` += `readyIpc` + عدّاد.
2. بلوك «جاهز للمستخلص» في عرض العقد (نمط كتلة الصيانة): زر «جهّز مستخلصًا»
   ⇒ `/invoices/new?customerId&contractId&paymentId` بملء مسبق (وصف «مستخلص إنجاز — العنوان»،
   مبلغ السطر، تاريخ اليوم).
3. `InvoiceNewPage` يقرأ `paymentId` من الاستعلام ويعرض مؤشر الربط ويرسله في POST.
4. `POST /api/invoices` يقبل `paymentId` اختياريًا: الدفعة بنفس العقد + **لا فاتورة نشطة
   بنفس الربط** (منع تكرار الجسر) — يُخزَّن.

### 2.5 ما لا يفعله الجسر (حدود — كالصيانة حرفيًا)
لا فاتورة آلية ولا قيد آلي ولا لمس للفترات المالية — الإصدار يبقى فعلًا صريحًا بشاشة الفواتير.

## 3) التسجيلات الإلزامية (درس T111)
- `db.ts`: TENANT_MODELS += `consultingRevision` (بعد models العقود/المهندسين — طوبولوجيًا).
- `backup-dump.ts`: BACKUP_MODELS += `{ model: "consultingRevision", table: "consulting_revisions", serial: true }` بعد العقود/المهندسين.
- عمود `invoices.payment_id` لا يحتاج تسجيلًا (عمود لا جدول).

## 4) الاختبارات
- نواة المراجعات: ترقيم revNo، آلة الحالات، إلزامية ملاحظة الإرجاع، مؤشرات KPI.
- جسر readyIpc: التصفية (مُثار/مغلق/غير مفوتر/متخطى مستبعد، الملغي يُهمل).
- `bun run db:push` ثم تحقق حي: إنشاء دورة → اعتماد → إرجاع؛ إغلاق مرحلة بدمعة مرتبطة ⇒ ظهور السطر في «جاهز للمستخلص» ⇒ تجهيز فاتورة ⇒ زوال السطر.
