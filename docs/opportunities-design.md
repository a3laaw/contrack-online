# تصميم ر3 — فرص البيع (CRM خفيف) · خط أنابيب قبل عرض السعر — ConTrack Online

> وثيقة تصميم للاعتماد — بلا أي كود. المرجع: موديول CRM في خريطة Odoo المعتمدة (`docs/odoo-modules-reference.md` §3.2: Opportunities/Pipeline/Lost reasons — بلا Teams ولا IAP ولا قنوات ويب) + الخارطة المعتمدة (`docs/development-roadmap.md` ر3). المحرك القائم الجاهز للاستثمار: **عروض الأسعار** (آلة حالات QUOTE_TRANSITIONS مغلقة + ترقيم QUO ذري + قبول العرض يفتح معالج العقد معبأً — ر1) + مهام المتابعة بالعميل (ر2).
> **الحالة: بانتظار موافقة المالك على هذا التصميم قبل التنفيذ.**

## 0) النطاق المعتمد — التقاط ما قبل التسعير بلا ازدواج

| # | البند | الوضع الحالي | ما تضيفه الفرص |
|---|-------|---------------|-----------------|
| 1 | ما قبل عرض السعر | لا شيء — العروض تدخل مباشرة في وحدة qc؛ الفرص التي لم تصل مرحلة العرض (والمرفضة قبل التسعير) تضيع بلا أثر | **جدول فرص** بخط أنابيب مرتّب: جديدة ← مؤهَّلة ← عُرض عليها ← مقبولة / مفقودة (بسبب خسارة) |
| 2 | ربط الفرصة بالعرض | لا ربط | زر «إصدار عرض سعر» من الفرصة يفتح **معالج العرض القائم حرفيًا** معبأً (العميل + وصف من الفرصة) ويسمّ العرض بالفرصة — عند القبول/الرفض تتحرك الفرصة تلقائيًا (قرار د4) |
| 3 | العميل غير الموجود بعد | العميل إلزامي في العرض | `customerId` **اختياري** في الفرصة — وزر «إنشاء عميل من الفرصة» يملأ نموذج العملاء القائم باسمها وهاتفها ثم يربط |
| 4 | معدل التحويل | لا يقاس | بطاقة ملخص: عدد الفرص لكل مرحلة + المبلغ المتوقع المفتوح + معدل التحويل (مقبولة ÷ المقفلة) — أرصدة اشتقاقية بلا جداول عدادات |

## 1) الفلسفة — نفس الأسس بلا استثناء

- **كيان واحد لا اثنان**: «Lead» و«Opportunity» في Odoo هي نفس الكيان بمرحلتين — فرص ConTrack جدول واحد ومرحلة أولى اسمها «جديدة» (درس G3: لا ازدواج كيان ولا مسار موازٍ).
- **العرض يبقى ملك qc**: الفرصة لا تعيد بناء العروض ولا آلة حالاتها — تستهلك المعالج والترقيم والانتقالات القائمة حرفيًا، وتربط فقط بـ`quotationId` (نمط ربط المجموعة في ر1).
- **الحركات المفتاحية آلية والباقي يدوي**: إصدار العرض/قبوله/رفضه يحرك المرحلة داخل معاملة الحدث نفسه — أما «جديدة→مؤهَّلة» وسبب الخسارة فيدويان بحراس انتقال مغلقين.
- **اختيارية بلا إجبار**: الموديول لا يُقترح آليًا من Onboarding ولا يظهر إلا بعد تفعيله — لا عبء إداري على من لا يريده (مخاطرة الخارطة معالجة بالتصميم).
- **النواة النقية أولًا** (نمط consulting-v1): حراس الانتقالات وحساب المؤشرات دوال نقية في `opportunities-core.ts` + اختبارات bun قبل أي ربط.

## 2) قرارات تحتاج اعتمادك (القيم الافتراضية المقترحة — تُعدل عند الاعتماد)

| # | القرار | المقترح | البديل |
|---|--------|---------|--------|
| د1 | الملكية والبلاطة | موديول **«فرص البيع»** مستقل (`crm`) بالكتالوج + بلاطة جانبية بجوار «العقود وعروض الأسعار» + مفتاح `screen_opportunities` (secretary:true) + `moduleGuard("crm")` — **لا يُقترح آليًا من Onboarding** (التفعيل يدوي من الإعدادات حصرًا) | دمجه بلاطة داخل المبيعات (يخلط التسعير بما قبله — والمبيعات منفذة ومستقرة `5d8bc46`) |
| د2 | المراحل الخمس | `جديدة · مؤهَّلة · عُرض عليها · مقبولة · مفقودة` — الانتقالات المغلقة: جديدة→مؤهَّلة/مفقودة · مؤهَّلة→عُرض عليها/مفقودة · عُرض عليها→مقبولة/مفقودة — **مقبولة ومفقودة نهائيتان** (المفقودة تسبب إلزاميًا) | مراحل حرة بلا حرس (يفقد خط الأنابيب معناه — مرفوض) |
| د3 | أسباب الخسارة | قائمة محدودة نصية: «سعر مرتفع · خسر المنافسة · تأجل العميل · لا تناسب لنا · أخرى» + حقل ملاحظة حر | نص حر بلا قائمة (يصعب قياس الأسباب لاحقًا) |
| د4 | المزامنة مع العرض | إصدار عرض من الفرصة ⇒ ربط + رفع المرحلة إلى «عُرض عليها» آليًا · قبول العرض في qc ⇒ «مقبولة» آليًا داخل معاملة القبول · رفض العرض ⇒ «مفقودة» آليًا بسبب «خسر المنافسة» قابل للتعديل | بلا مزامنة (يتعقب المستخدم يدويًا ما يفعله النظام تلقائيًا في Odoo — مرفوض) |
| د5 | إنشاء العميل | زر «إنشاء عميل من الفرصة» في حوار الفرصة يفتح نموذج العملاء القائم معبأً بالاسم/الهاتف؛ بعد الحفظ تُربط الفرصة به فورًا (المرحلة لا تتغير) | إدخال معرف العميل يدويًا فقط (احتكاك يومي بلا داعٍ) |
| د6 | رقم الفرصة | ترقيم ذري `nextNumberByKey("opportunity:number","OPP",4,tx)` بمزامنة العدّاد فوق الأرقام القائمة أول استخدام (نمط QUO/CPR/Voucher) | ترقيم max+1 (سباقان موثقان في الجلسات السابقة — مرفوض) |
| د7 | المصدر | قائمة قصيرة: «مكالمة · زيارة · توصية عميل · معرض/فعالية · أخرى» اختيارية | نص حر (قياس المصادر يصير ضربًا في البحر) |

## 3) المخطط (Prisma) — جدول واحد بلا جداول مرافقة

```prisma
model Opportunity {
  companyId          Int       @default(1) @map("company_id")
  id                 Int       @id @default(autoincrement())
  opportunityNumber  String    @map("opportunity_number")            // OPP-0001 ذري (د6)
  name               String                                           // وصف الفرصة الحر
  customerId         Int?      @map("customer_id")                   // اختياري — د5
  customer           Customer? @relation("OpportunityCustomer", fields: [customerId], references: [id])
  stage              String    @default("جديدة")                      // د2 — قائمة مغلقة
  expectedAmount     Decimal   @default(0) @map("expected_amount") @db.Decimal(18, 3)
  expectedCloseDate  String    @default("") @map("expected_close_date") // YYYY-MM-DD
  source             String    @default("")                          // د7
  quotationId        Int?      @map("quotation_id")                  // أول عرض صدر منها (نمط SetNull)
  quotation          Quotation? @relation("OpportunityQuotation", fields: [quotationId], references: [id])
  lostReason         String    @default("") @map("lost_reason")      // د3 — إلزامي عند «مفقودة»
  notes              String    @default("")
  createdBy          Int?      @map("created_by")
  createdAt          DateTime  @default(now()) @map("created_at")
  updatedAt          DateTime  @updatedAt @map("updated_at")

  @@unique([companyId, opportunityNumber])
  @@index([companyId, stage])
  @@index([customerId])
  @@map("opportunities")
}
```
- على `Quotation`: علاقة عكسية واحدة فقط `opportunities Opportunity[]` — لا أعمدة جديدة (الربط بجهة الفرصة).
- لا enum — `OPPORTUNITY_STAGES` + `OPPORTUNITY_LOST_REASONS` + `OPPORTUNITY_SOURCES` في `opportunities-constants.ts` (قاعدة ConTrack).
- التسجيلات الإلزامية: `TENANT_MODELS` + `BACKUP_MODELS` + `nav-structure.ts` + `modules-catalog.ts` (code "crm" مُعلن «تتبع الفرص التجارية قبل التسعير») — قبل تنفيذ أي شاشة.

## 4) النواة النقية (`opportunities-constants.ts` + `opportunities-core.ts`)

- `OPPORTUNITY_TRANSITIONS` خريطة مغلقة (د2) + `assertTransition(from,to)` برسالة عربية «الانتقال الممنوع».
- `normalizeLostReason(stage, reason)`: «مفقودة» بلا سبب تُرفض نقيةً.
- `pipelineKpis(rows)`: { byStage, openExpected, closedCount, wonCount, conversionRate } — حساب اشتقاقي خالص.

## 5) الخادم (المسارات — نمط consulting حرفيًا)

| المسار | الأفعال | الحراسة |
|--------|---------|---------|
| `GET/POST /api/opportunities` | قائمة بفلاتر (مرحلة/عميل/نص/فترة) + إنشاء | ترقيم OPP ذري داخل المعاملة · stage افتراضي «جديدة» |
| `GET/PATCH/DELETE /api/opportunities/[id]` | تفصيل + تعديل (المرحلة بحرس الانتقالات) + حذف | **حذف الفرصة المرتبطة بعرض مرفوض** برسالة عدد العروض (نمط حماية الاستشارات) — المقفلة لا تُعدَّل المرحلة |
| `POST /api/opportunities/[id]/quotation` | «إصدار عرض سعر من الفرصة» | يعيد حمولة تعبئة معالج العرض القائم (customerId اختياري → إن لم يوجد يطلب إنشاء العميل أولًا) — **الربط والمرحلة في معاملة إصدار العرض نفسها** (د4) |
| `GET /api/opportunities/summary` | مؤشرات خط الأنابيب | اشتقاقية بلا عدادات |

- **القُطْب على qc**: عند قبول/رفض العرض المرتبط، تعديل المرحلة يحدث داخل معاملة حدث العرض القائم (سطران — لا مسار كتابة ثانٍ).
- audit كامل التغييرات على الفرصة (نمط ConsultingProject).

## 6) الواجهة — شاشة «فرص البيع» واحدة

- **الشل**: بلاطة «فرص البيع» في الجانبي (+ مرآة `ModuleTabsBar` للهاتف) — الشاشة نفسها: بطاقة ملخص أعلى (مراحل بأعدادها + المبلغ المفتوح + معدل التحويل بشارات NOVA) + جدول الفرص (الرقم · الاسم · العميل · المرحلة شارة ملونة · المبلغ المتوقع · الإغلاق المتوقع · المصدر · العرض المرتبط رابطًا).
- **حوار إنشاء/تعديل**: الاسم · العميل (بحث) مع زر «إنشاء عميل من الفرصة» (د5) · المرحلة (قائمة الانتقالات المسموحة فقط — نمط قائمة حالة العرض في ر1) · المبلغ والتاريخ المتوقعان · المصدر · سبب الخسارة عند «مفقودة» · ملاحظات.
- **زر «إصدار عرض سعر»** يظهر على الجديدة/المؤهَّلة/عُرض عليها — يفتح معالج العرض القائم معبأً (لا شاشة عروض جديدة — درس G3/G5).
- الجوال 375 بلا تمرير أفقي · تمرير طولي `max-h-96 overflow-y-auto` للقوائم · تذييل مثبت (`min-h-screen flex flex-col` + `mt-auto`) · ألوان NOVA حصرًا (المراحل: جديدة كهرماني فاتح · مؤهَّلة برتقالي أساسي · عُرض عليها أزرق ملكي معلوماتي · مقبولة رمادي مكتمل · مفقودة أحمر خطر).

## 7) دروس NovaFlow والنظام المطبقة

- **G3/G5**: لا كيان موازٍ للعروض ولا شاشة عروض ثانية — الفرصة تستهلك معالج qc القائم.
- **G7/G11**: المراحل والمصادر والأسباب مفردات معرفية بجداول ثابتة؛ الربط بالعميل والعرض معرفي لا نصي.
- **G9**: المؤشرات اشتقاقية بلا جداول عدادات.
- **معاملة واحدة**: ربط العرض + تحريك المرحلة + audit في معاملة إصدار العرض؛ القبول/الرفض في معاملة حدث العرض.

## 8) خطة التنفيذ والاختبارات (بعد الاعتماد)

1. النواة النقية + اختبارات bun (الانتقالات · سبب الخسارة الإلزامي · المؤشرات).
2. السكيمة (`db push` — جدول جديد لا يلمس شيئًا) + التسجيلات الأربع.
3. المسارات الخمسة + قُطْب qc (قبول/رفض/إصدار).
4. الشاشة والشل والمرآة → تحقق حي: إنشاء OPP-0001 → مؤهَّلة → إصدار عرض يربط ويرفع المرحلة → قبول العرض يجعلها «مقبولة» آليًا → فرصة أخرى «مفقودة» بسبب إلزامي → المؤشرات صحيحة → جوال 390 → lint صفر.

## 9) حدود الموديول (ما لا يُبنى عمدًا)

- لا Leads منفصلة عن الفرص · لا فرق بيع (Teams) · لا تنقيب/إثراء IAP · لا قنوات ويب ولا لايف شات · لا قوائم أسعار (مال ر4) · لا تقويم CRM — مهام المتابعة القائمة بالعميل (ر2) تبقى بيتها ولا تُربط بالفرصة إلا بأمر لاحق من المالك.
