## 2) القرار المعماري — لماذا نموذج أنشطة لا عمودان؟

البرنامج الحقيقي يحتوي ≈600 نشطة مقابل 527 بند BOQ، والعلاقة ليست 1:1 إطلاقاً:
- أنشطة **بلا قيمة** (تسليمات/اعتمادات/شراء/جهات) لا تنعكس على أي بند لكنها حاسمة زمنياً (مسار تسليم المواد يحكم بدء التركيب).
- نشاط واحد (`INST. OF BLOCK WALLS`) يمتد على بنود متعددة، والبند الواحد يُنفّذ عبر عدة مستويات (`P-FL…P-FF`).
- تواريخ **Early وLate معاً** = Float مجاني — غير قابل للتخزين في عمودين.

**إذن — نموذجان جديدان (إضافية صرفة، G9: صفوف مؤرخة محفوظة أبدياً):**

```prisma
/// دفعة استيراد للبرنامج الزمني — أحدث دفعة = الحيّ، القديمة محفوظة (نمط Baseline R01/R02)
model ScheduleImport {
  companyId      Int      @default(1)
  id             Int      @id @default(autoincrement())
  contractId     Int
  contract       Contract @relation(fields: [contractId], references: [id], onDelete: Cascade)
  fileName       String
  revision       String   @default("")   // R01 من تذييل الملف إن وُجد
  dataDate       String   @default("")   // Data Date — لحظة صحة الجدول
  projectStart   String   @default("")   // 28-Feb-26
  projectFinish  String   @default("")   // 27-May-27
  activityCount  Int      @default(0)
  workCount      Int      @default(0)    // أنشطة تحمل قيمة (P-*/X-*)
  warnings       String   @default("")   // JSON تحذيرات المحلل
  importedBy     String   @default("")
  createdAt      DateTime @default(now())
  activities     ScheduleActivity[]
  @@index([contractId])
  @@map("schedule_imports")
}

/// نشطة البرنامج الزمني — تواريخ أصلية كما وصلت (لا مشتقات مخزنة)
model ScheduleActivity {
  companyId      Int             @default(1)
  id             Int             @id @default(autoincrement())
  importId       Int
  import         ScheduleImport  @relation(fields: [importId], references: [id], onDelete: Cascade)
  contractId     Int
  activityCode   String          @default("")  // كما ورد حرفياً بعد التطبيع
  name           String
  kind           String          @default("work") // work|submittal|approval|procurement|shopdrawing|testing|authority|closeout|general|summary
  family         String          @default("")  // P-FL | E-MA | U-GE … من البادئة
  durationDays   Int             @default(0)
  earlyStart     String          @default("")  // YYYY-MM-DD
  earlyFinish    String          @default("")
  lateStart      String          @default("")
  lateFinish     String          @default("")
  isSummary      Boolean         @default(false) // صف W band
  groupName      String          @default("")  // أقرب band حاوي (تقريبي — §3)
  divisionCode   String          @default("")  // من مطابقة القسم — §4
  boqItemId      Int?            // ربط مبكر اختياري (ب3) — الافتراضي مطابقة بالقسم
  sortOrder      Int             @default(0)
  @@index([importId])
  @@index([contractId, divisionCode])
  @@map("schedule_activities")
}
```

وعلى `BoqItem` (من قرار dashboard §2 — يبقى كما هو): `plannedStart / plannedFinish` — لكن الاستيراد **يملؤهما آلياً** من نافذة قسم البند (§4)، فيبقى عقد العرض في اللوحة سليماً بلا إدخال يدوي.

**لماذا هذا ليس «بناء نظام جديد»؟** جدولان صرف + محلل + روتين استيراد — نفس نمط `boq-parse`/`boq-import` المنجز والمجرّب حرفياً. كل ما عداها (PV/EV/SPI) مشتقات تُحسب لحظة العرض.

## 3) المحلل النقي `src/lib/import/schedule-parse.ts` (بلا db — مرآة boq-parse)

- **المدخلات المقبولة (v1):**
  1. **PDF مباشرة** — الملف الحالي: استخراج نص عبر `pdf-parse` (تبعية جديدة صغيرة pure-JS) ثم محلل نصي. بنيته الجدولية استخرجت من الاختبار بشكل ممتاز (كل سطر: كود + اسم + مدة + 4 تواريخ).
  2. **Excel/CSV من Primavera** — الأضمن للمستقبل (أي تحديث R02 يُصدَّر بنفس الأعمدة) — إعادة استخدام `exceljs` الموجود.
- **قواعد المسح:**
  - سطر نشطة: `[كود]? [اسم] [مدة رقمية] [تاريخ] [تاريخ] [تاريخ]? [تاريخ]?` — الصفوف بلا كود = **summary bands** (تلتقط اسمها كـgroup حاوي للأسطر التالية حتى band التالي، بلا تداخل مُدّعى — الـPDF يفقد الإزاحة فالتقسيم تقريبي ومعلن كحد).
  - تطبيع الكود: إزالة الالتصاق بالاسم (regex للأقسام المعروفة `^[A-Z]{1,2}(-[A-Z]{2,3})+[-]?\d+` ثم فصل الباقي)، توحيد الشرطات.
  - تواريخ `DD-MMM-YY → YYYY-MM-DD` بجدول أشهر ثابت (Feb/Mar/…) — لا اعتماد على locale.
  - صفر مدة + Start=Finish = Milestone (يُخزن كما هو).
- **التحقق بعد المسح (يُعرض في المعاينة):**
  - عدد الأنشطة الكلي / work / summary — و`projectStart/Finish` = min(earlyStart)/max(earlyFinish) يجب أن يطابقا 28-Feb-26/27-May-27 وإلا تحذير.
  - كل نشاط work حصل على divisionCode؟ (عدّاد غير المطابق يظهر بأسمائه — لا يُرفض الاستيراد، يُترك بلا قسم).
  - تواريخ ناقصة/غير قابلة للتحويل → تحذير مفرد.

## 4) المطابقة بالأقسام وتعبئة البنود (قلب «متأخرين فين متقدمين فين»)

- **قاموس مرادفات ثابت في المحلل** يربط أسماء bands المستويات بأقسام BOQ المستوردة (نفس القسمان الـ18 من الملف الحقيقي):

| Band في البرنامج | قسم BOQ (divisionCode) |
|---|---|
| CONCRETE WORK | 03 CONCRETE |
| MASONRY WORK | 04 MASONRY |
| METAL WORK | 05 METAL |
| THERMAL & MOISTURE PROTECTION | 07 THERMAL |
| WOODEN/STEEL/ALUMINUM DOORS & WINDOWS | 08 DOORS |
| WALL/FLOOR/CEILING FINISHES · SPECIALTIES · FURNISHING | 09 FINISHES |
| MECH. (PLUMBING/F.FIGHTING/HVAC) | 15 MECH |
| ELEC. (POWER/LIGHTING/DATA/FIRE ALARM/CCTV/…) | 16 ELEC |
| SITE WORK · EXCAVATION · LANDSCAPE · EXTERNAL | أقسام الأعمال الخارجية المقابلة |

- **شاشة معاينة المطابقة** (نمط معاينة BOQ): كل قسم BOQ × النافذة الزمنية المشتقة من أنشطة work لمطابقته `[min earlyStart → max earlyFinish]` + عدد الأنشطة + قيمة القسم من BOQ — المالك يرى كل شيء قبل التأكيد.
- **تعبئة `BoqItem.plannedStart/plannedFinish`:** لكل بند = نافذة قسمه (بدقة البند الواحد تُحسَّن في ب3 بربط مباشر). هكذا يتحقق حرفياً «عندي برنامج زمني معروف كل بند هيخلص امتي» — لكل بند تاريخا بدء ونهاية مخططان مشتقان من CPM الحقيقي لا من إدخال يدوي.
- **PV (القيمة المخططة) على مستوى القسم:** قيمة القسم (Σ مبالغ بنوده) توزَّع خطياً داخل نافذته — وهذا بالضبط مستوى دقة لوحة الاستشاري المرفقة سابقاً («تقدم بالأقسام» 16 قسماً). التوزيع داخل القسم على الأنشطة (منحنى أدق) = ب3.

## 8) ج1 المتبقي — النافذة المخططة لكل بند: التحرير اليدوي + العرض الزمني (الجلسة 26)

> **السياق:** ب1 (الاستيراد وتعبئة plannedStart/plannedFinish من نافذة القسم) منفذة ومتخذة حيًا، ود1 أُغلقت (الجلسة 25) — متطلبات ج1 اكتملت. هذا القسم يغلق ما تبقى من ج1 وفق `project-dashboard-design.md` §2/§6: «شبكة إدخال/تحرير سريعة» + البرنامج الزمني للبنود **مرئيًا** — فوق القائم حصرًا، بلا جداول جديدة (النافذة عمودان على `BoqItem` موجودان منذ ب1).

### 8.1 النواة النقية `src/lib/schedule-items-core.ts` (بلا DB — مرآة نمط د1)

| الدالة | العقد |
|---|---|
| `validatePlannedWindow(start, finish)` | الفارغَان معًا = إفراغ مقبول (توافق خلفي كامل — بلا نافذة سلوك ب1 حرفيًا) · نصف نافذة (أحدهما بلا الآخر) مرفوضة · الصيغة YYYY-MM-DD إلزامية · البداية ≤ النهاية — رسائل عربية تُعرض كما هي بالمسار والواجهة |
| `deriveProjectWindow(rows)` | محور المشروع = min(plannedStart)/max(plannedFinish) للبنود ذات النافذة — بلا بنود بنافذة ⇒ null |
| `scheduleItemStatus(row, today)` | `none` بلا نافذة · `upcoming` اليوم < البداية · `active` داخل النافذة · `overdue` اليوم > النهاية |
| `windowBarPct(row, pStart, pFinish)` | موضع الشريط وعرضه % على المحور (تقريب منزلتين — حصيّة رياضية قابلة للاختبار) |
| `scheduleItemsView(rows, today)` | الاشتقاق الكامل للعرض: صفوف مرتبة زمنيًا (بلا نافذة آخرًا بالترتيب الأصلي) + شريط كل بند + إجماليات {total, withWindow, active, overdue, upcoming} |

### 8.2 المسارات — توسيع القائم حصرًا (لا مسارات جديدة)

- `PATCH /api/contracts/[id]/boq?itemId=` يقبل `plannedStart/plannedFinish` — التحقق عبر النواة (فارغ = إفراغ النافذة صراحةً).
- `POST /api/contracts/[id]/boq` يقبل الحقلين عند الإضافة اليدوية.
- القراءة كما هي: `GET /boq` يرد بها منذ ب1 — العرض الزمني مشتق في العميل منها (G9).

### 8.3 الواجهة — فوق مكونات ب1 حصرًا

1. **جدول البنود (سطح المكتب):** خلية «النافذة المخططة» تتحول زر تحرير للمدير — حوار تعيين صغير: حقلَا تاريخ + زر **«مطابقة قسمه»** (يملي من نوافذ الأقسام المشتقة `GET /schedule` إن وُجد استيراد) + زر إفراغ.
2. **قسم «النافذة لكل بند» في ScheduleSection** (قلب «برنامج زمني للبنود»): جدول مرتب زمنيًا — البند/الوصف/القسم/النافذة/**شريط النافذة على محور المشروع** + شارة الحالة (`جارية/قادمة/متجاوزة`) + أيام متبقية/تجاوز — فلتر بالقسم + `max-h-96 overflow-y-auto` (قاعدة القوائم الطويلة) + بطاقات جوال.
3. **بطاقة الجوال للبند:** سطر النافذة ببطاقة البند القائمة (تناسق 390).
- **حدود صريحة:** لا PV/EV (ب2/ج2) ولا شجرة أنشطة (ب3) ولا قراءة تنفيذ هنا — الجدولة حصرًا.

## 12) ب2 — محرك PV المخطط: الاستحقاق الخطي الشهري/التراكمي بالأقسام + بطاقة «تقدم مخطط» (الجلسة 32)

> **السياق:** ب2 وفق §6 (الاعتمادية: ب1✓ الجلسة 6 + ج1✓ الجلسة 26) — الترتيب الكلي: ~~ب1~~ ← ~~ز1~~ ← ~~ز2~~ ← ~~ز3~~ ← ~~د1~~ ← ~~ج1~~ ← ~~م1~~ ← ~~ج2~~ ← ~~ج3~~ ← ~~م2~~ ← ~~م3~~ ← **ب2** ← ب3. **صفر تغييرات مخطط** — لا جداول ولا أعمدة ولا enums: المحرك مشتق لحظيًا فوق النوافذ القائمة (ب1/ج1) وفق G9.

### 12.1 القرار الحاكم — ترقية دلالة PV من «خطوة عند النهاية» إلى «استحقاق خطي داخل النافذة»

- ج2 بنى PV بخطوة عند `plannedFinish` (تبسيط v1 معلن: «المخطط خطوة عند كل plannedFinish — مبكر حصرًا»). §4 من هذه الوثيقة وثّق الأساس الحاكم قبل ذلك بك: **«قيمة القسم توزَّع خطياً داخل نافذته — وهذا بالضبط مستوى دقة لوحة الاستشاري»**. ب2 يرفع المحرك إلى الأساس الموثق: **استحقاق خطي** لكل بند داخل نافذته — القيمة × الأيام المنقضية (شاملة البداية) ÷ أيام النافذة (شاملة الطرفين، نمط الرأس ج2 `daysBetween+1`) — فيصبح SPI مؤشر تدرج حقيقيًا بدل القفز صفر→كامل، والمنحنى المخطط منحنى فعلًا لا درجات.
- **القواعد المحفوظة حرفًا من ج2:** بلا نافذة ⇒ خارج PV حصرًا · قيمة ≤ 0 ⇒ لا مساهمة · التاريخي asOf: الاستحقاق حتى asOf حصرًا (§8.2.11) · النافذة الناقصة (بداية غائبة والنهاية موجودة — يمنعها تحقق ج1 لكن الحارس لا ينكسر) ⇒ سقوط لسلوك الخطوة عند النهاية (توافق خلفي).
- **المنحنى المخطط الشهري:** نقطة التراكمي الشهري عند نهاية كل شهر (دقة شهرية = دقة الاستشاري §4) — `deriveEvmSCurve` تبقى بتوقيعها والمخطط يمر إليها بمفتاح نهاية الشهر بدل تاريخ نهاية البند.

### 12.2 النواة النقية `src/lib/pv-plan-core.ts` (بلا I/O)

| الدالة | العقد |
|---|---|
| `accrueLinear(value, start, finish, d)` | استحقاق بند واحد حتى d: صفر قبل البداية · كامل من النهاية فصاعدًا · خطي بينهما بأيام شاملة — **بلا بداية ⇒ خطوة عند النهاية** (توافق خلفي) — قيمة ≤ 0 ⇒ صفر |

### 12.3 الدمج بنواة ج2 (evm-core) — بلا مساس بالإشارات النهائية

`deriveEvm` يستبدل كتلة PV الخطوة بالمحرك: `pv` و`pvPct` و`plannedByDate` (بمفتاح نهاية الشهر) و`divisions.plannedPct` كلها من الاستحقاق الخطي — وSPI/CPI/EAC/التحذيرات تعتمد على pv المحدث آليًا بلا تغيير في منطقها (القسمة على صفر null كما هي §8.2.5). المخرج يزيد `pvPlan.byMonth` (نفس الدلاء) للواجهة.

### 12.4 الواجهة — بطاقة «تقدم مخطط» في EvmDashboardSection

بعد بطاقة التقدم الإجمالي مباشرة: النسبة المخططة الكبرى (`pvPct`) بقيمة `pv` الحالية + **جدول شهري** (الشهر / المخطط بالشهر / التراكمي) بـ`max-h-96 overflow-y-auto` (قاعدة القوائم الطويلة) + بطاقات جوال مرآة — قراءة حصرًا. المسار يرد بها ضمن `evm` بلا مسار جديد.

### 13.2 المسارات — القائم يوسع + مسار كتابة واحد

- `GET /schedule` يضيف `activities` (غير الملخصة من أحدث دفعة، مع float المشتق ورقم البند المربوط) — الشجرة والتوزيع يشتقان بالعميل من الصفوف (G9).
- `PATCH /api/contracts/[id]/schedule/activity` بحرس `action_edit_contract` (نمط PATCH boq حرفيًا): `{activityId, boqItemId}` — null = فك الربط — تحقق ملكية مزدوج (النشطة للعقد · البند للعقد وغير محذوف) — رسائل عربية كما هي.
- `GET /dashboard` يرفع النوافذ: البند المربوط بنشطاته المؤرخة ⇒ نافذته من `deriveItemWindowFromActivities` (**الربط المباشر يجري EVM بدقة الأنشطة**) — غير المربوط بنافذته المخزنة (ب1/ج1) — الأنشطة تسبق التخزين حين تُؤرخ.

### 13.3 الواجهة — قسم «شجرة الأنشطة» في ScheduleSection + التوزيع الشهري المشتق

1. **شجرة الأنشطة** بعد نوافذ الأقسام: bands قابلة للفتح (حالة عميل — أول band مفتوح افتراضيًا)، صف النشطة: الكود/الاسم/شارة النوع/التواريخ/المدة/Float بشارته (**حرج عند الصفر**)/بند مربوط — ربط للمدير بحوار منتقي البنود (مرشح بقسم النشطة أولًا) وفكّ بضغطة — `max-h-96 overflow-y-auto` وبطاقات جوال بلمس 44px.
2. **التوزيع الشهري بالأقسام من الأنشطة** (منحنى أدق §4): منتقي قسم + جدول شهري (الشهر/المخطط/التراكمي — النهاية = قيمة القسم) مشتق بالعميل من `distributeSectionAcrossActivities` فوق أنشطة القسم وقيمة القسم من الاستجابة — بلا مساس بـPV الإداري للبنود (أساس EVM بند-مستوى ب2 حصرًا).
