## 0) المبدأ الحاكم

- **قيد واحد متوازن إلزامي** — كل إضافة مالية تمر عبر `postJournalEntry` (لا قيود جانبية).
- **أرصدة اشتقاقية** حيث يمكن، **لقطات مجمّدة** حيث يجب (تراكم المستخلص لحظة الاعتماد).
- **كل جدول يُستخدم فورًا** — لا كيانات شبح.
- الحسابان 1122 (محتجزات العملاء) و2121/2122 (مستحقات/محتجزات الباطن) **مبذوران في الدليل الموحد** (`accounting-core.ts` L106/L171) — المحرك هو الجديد فقط.

## 1) المحتجزات على مستخلص العميل (Retention)

### 1.1 الحقول على `Invoice`
| الحقل | النوع | الدلالة |
|---|---|---|
| retentionRate | Decimal(5,2) | النسبة المحتجزة من صافي الفاتورة (0-25) |
| retentionAmount | Decimal(18,3) | المحتجز الفعلي = round3(total × rate/100) |
| retentionReleased | Boolean | هل أُفرج عنه (أُطلق للتحصيل) |
| retentionReleasedAt | String | تاريخ الإفراج YYYY-MM-DD |
| retentionReleaseEntryId | Int? → JournalEntry | قيد الإفراج (علاقة `RetentionReleaseEntry`) |

### 1.2 قيد الإصدار الموسّع (3 أسطر عند وجود محتجزات)
```
مدين  ذمم العملاء / الفرعي الآلي (1121xxx)   total − retention
مدين  محتجزات العملاء (1122)                  retention
دائن  إيرادات العقود (4100)                   total
```
التوازن: (total−R) + R = total ✓. **بلا محتجزات = السطران القائمان حرفيًا** (تغيير جذري صفر على المسار الحالي). الإلغاء والتعديل يعكسان/يعيدان النشر بالأسطر المخزنة آليًا (`reverseJournalEntry` يقرأ الأسطر الفعلية).

### 1.3 «المطلوب نقدًا» (netDue)
`netDue = total − retentionAmount − advanceRecovered` — حقل عرض مشتق لا مخزّن.
سندات القبض تخصص على total كالعادة: بعد سداد netDue تصبح الفاتورة «مسددة جزئيًا» والمتبقي = المحتجزات (شارة واضحة) حتى الإفراج والتحصيل.

### 1.4 الإفراج (release)
`POST /api/invoices/[id]/retention-release` (مدير/سوبر — `adminGuard`):
- الحواجز: غير ملغاة · retentionAmount > 0 · غير مفرج عنه سابقًا · فترة التاريخ مفتوحة.
- القيد: **مدين ذمم/فرعي العقد / دائن 1122** بمبلغ R (نقل الالتزام من محتجز إلى ذمم قابلة للتحصيل) ثم يُحصَّل بسند قبض عادي.
- يسجّل حدث عقد «إفراج عن محتجزات» + تدقيق.

### 1.5 السقف
سقف الفوترة يظل على **total (الإجمالي المفوتر)** — المحتجزات جزء من مستحق العقد لا خصم منه (كما في NOVA IPC).

## 2) الدفعة المقدمة واستردادها (Advance)

### 2.1 الحقول
- `Contract` += `advanceAmount` (18,3 — قيمة الدفعة المستلمة من العميل) + `advanceRecoveryPct` (5,2 — نسبة الاسترداد من كل مستخلص).
- `Invoice` += `advanceRecovered` (18,3) — **لقطة محسوبة خادميًا** عند الإصدار:
  `advanceRecovered = min(round3(total × pct/100), advanceAmount − Σ advanceRecovered للفواتير غير الملغاة الأخرى)`.
- `SubContract` += نفس الحقلين (دفعة مقدمة **لصالح** المقاول الباطن) — تُسترد من مستخلصاته بنفس النمط.

### 2.2 لماذا لا يدخل الاسترداد القيد؟ (قرار معلن)
سند القبض الزائد عن المستحق يُسجل حاليًا **دائن ذمم العملاء** (رسالة «تُسجل الزيادة كدفعة مقدمة» في `prepareVoucher` L858) — أي أن أثر الدفعة المحاسبي سُجل على الذمم عند الاستلام. لو خُصم الاسترداد من قيد الفاتورة أيضًا (دائن 2140) لازدوج الأثر وعاد عطل NOVA في عدم التوازن الاقتصادي (ليس التوازن الحسابي) — **فالاسترداد جدولة تحصيل لا حركة حساب**، و`advanceRecovered` يوثق الجدولة ويقود «المتبقي من الدفعة».

### 2.3 تعديل حقول العقد
`PATCH /api/contracts/[id]` يقبل `advanceAmount`/`advanceRecoveryPct` (مع حدث عقد). تغيير النسبة يؤثر على المستخلصات الجديدة فقط — اللقطات المخزنة لا تُمس.

## 3) مستخلص الباطن SubIPC

### 3.1 `SubCertificate` (sub_certificates)
| الحقل | النوع |
|---|---|
| subContractId → SubContract | Cascade معه |
| certNo | Int — تسلسلي **لكل عقد باطن** (unique معه) |
| certNumber | String — عرض SUBIPC-#### عبر عدّاد `nextNumber("SUBIPC")` |
| certDate / periodFrom / periodTo | String |
| grossAmount | 18,3 — محصلة أسطر الأعمال المنفذة |
| retentionRate / retentionAmount | 5,2 / 18,3 |
| advanceRecovery | 18,3 — استرداد الدفعة المقدمة (لقطة آلية) |
| otherDeductions / otherDeductionNote | 18,3 / String |
| netAmount | 18,3 = gross − retention − advanceRecovery − other (≥0) |
| cumulativeAmount | 18,3 — **لقطة التراكمي لحظة الاعتماد** |
| status | مسودة → مقدم → معتمد → مدفوع (وملغي) |
| submitBy/submitAt · approveBy/approveAt | سجل الحسم |
| paidVoucherId → Voucher | سند الصرف المرتبط |
| cancelReason | للملغي |

### 3.2 `SubCertificateLine` (sub_certificate_lines)
`certificateId (Cascade) · subItemId → SubContractItem? · description (لقطة) · qty · unitPrice · amount · cumulativeQty (لقطة الاعتماد)`.

### 3.3 آلة الحالات (G7 — مغلقة، القرار نهائي)
```
مسودة ──تقديم──▶ مقدم ──اعتماد──▶ معتمد ──صرف──▶ مدفوع
   │               │               │
   └───────────────┴───────────────┴──▶ ملغي (بسبب) — لا إلغاء للمدفوع (عبر إلغاء سنده)
تعديل/حذف: مسودة حصرًا · الصرف: معتمد حصرًا
```

### 3.4 التراكمي الكمي
متاح البند = `item.qty − Σ كميات المستخلصات غير الملغاة السابقة`. يُرفض سطر يتجاوز المتاح. عند الاعتماد تُجمَّد اللقطات (cumulativeQty لكل سطر + cumulativeAmount للمستخلص) — الدرس: الاعتماد هو لحظة الحقيقة، لا الإنشاء.

### 3.5 الصرف والبوابة والسقف — بلا ازدواج
الصرف يتم عبر `createVoucher` القائم: **بوابة تحصيل العميل (`subPayClientGate`) وسقف الصرف (`subPaymentCap`) والحساب البنكي تعمل تلقائيًا** لأن سند المستخلص سند صرف باطن عادي (`subContractId + partyType=subcontractor`). إلغاء السند لاحقًا ⇒ **رجوع المستخلص إلى «معتمد»** تلقائيًا (خطاف داخل `cancelVoucherTx`).

### 3.6 قرار معلن: لا ترحيل خاص إلى 2122
مسودة الخطة اقترحت ترحيل «2122 محتجزات مقاولي الباطن». بعد جس الكود: سند صرف الباطن يُقيد **دائن البنك بالمصروف فقط** — وما لم يُصرف يبقى دائنًا في **2121 مستحقات الباطن** تلقائيًا (المحتجز جزء منه). ترحيل 2122 منفصلًا يخالف حسابين لالتزام واحد. **القرار:** محتجز الباطن حقل رصد ومؤشرات على المستخلص، والإفراج عنه = سند صرف لاحق عبر الشاشة القائمة (نمط «تطوير لا ازدواج»). 2122 يبقى للحسم التاريخي القديم (LEGACY_ACCOUNT_MAP).

## 4) المسارات الجديدة

| المسار | الدور |
|---|---|
| `GET/POST /api/sub-certificates` | قائمة بعقد الباطن (+فلتر subContractId/status) · إنشاء مسودة |
| `GET/PATCH/DELETE /api/sub-certificates/[id]` | عرض كامل · تعديل مسودة · حذف مسودة |
| `POST .../[id]/submit` · `/approve` · `/cancel` | آلة الحالات (الإلغاء بسبب) |
| `POST .../[id]/pay` | سند صرف عبر createVoucher + تعليم مدفوع |
| `POST /api/invoices/[id]/retention-release` | إفراج محتجزات العميل (مدير) |
| `PATCH /api/contracts/[id]` | += advanceAmount/advanceRecoveryPct |
| `GET /api/contracts/[id]/pay-view` | += ملخص المحتجزات/الدفعة + مؤشرات مستخلصات الباطن |

التسجيلات الإلزامية: `db.ts` TENANT_MODELS += subCertificate/subCertificateLine · `backup-dump.ts` BACKUP_MODELS += الجدولان بعد subPaymentSource.

## 5) الواجهات

1. **فاتورة جديدة**: عند اختيار عقد — حقل «نسبة المحتجزات %» (أزرار سريعة 0/5/10) + سطر معلومات الدفعة المقدمة (استرداد تقديري) + شريط الإجماليات يصبح: قبل الخصم · الخصم · **الإجمالي المفوتر** · المحتجزات · **المطلوب نقدًا**.
2. **شاشة الفواتير**: شارة المحتجزات (X ك د.ك — مُفرج/معلّق).
3. **صفحة «الدفعات والمقاولون» بالعقد**: بطاقة «المحتجزات والدفعة المقدمة» (محتجز تراكمي/مفرج/قائم + دفعة/مسترد/متبقٍ) وجدول الفواتير ذات المحتجزات المعلقة بزر «إفراج».
4. **بطاقة العقد الباطن (تفاصيل موسعة)**: قسم «مستخلصات الباطن (SubIPC)» — جدول المستخلصات بآلة حالاتها + نافذة إنشاء ببنود من بنود العقد (كمية هذا المستخلص مقابل المتاح) + خصومات (نسبة محتجزات/استرداد آلي/أخرى) + أزرار تقديم/اعتماد/صرف/إلغاء + مؤشرات (تراكمي معتمد/مدفوع/محتجز).

هوية NOVA: `text-primary-ink` للأرقام الرئيسية، `formatKWD` بالأرقام الموحدة، جداول `max-h-96 overflow-y-auto`، شريط سفلي مثبت، موبايل 375 بلا تمرير أفقي.

## 6) حدود التصميم (ما لا يُفعل)
- لا فواتير آلية من مستخلص الباطن (الصرف سند مباشر — نمط الجسر القائم).
- لا تغيير على منطق سندات القبض/الصرف القائم — كل شيء عبر `createVoucher`.
- لا ترحيل 2122 (§3.6) ولا حساب دفعات مقدمة جديد (§2.2).
- لا محتجزات على فاتورة بلا عقد (المحتجزات مفهوم تعاقدي على مستخلص عقد).
