# خريطة التطوير القادم وفق بروتوكول القرار — ConTrack ↔ Odoo

> التاريخ: 2026-11-16 · المصدر: قرار المالك «هذا المرفق يعتبر خريطة للتطوير القادم»
> والمرجع المرفق (`odoo_modules_reference.md` → مُعتمد في `docs/odoo-modules-reference.md`).
> **هذه الوثيقة للعرض والموافقة — لا كود قبل اعتماد المالك للأولويات.**

---

## 1) تبنّي بروتوكول القرار — معدّلاً لـ ConTrack

المرجع مكتوب لأنظمة Odoo؛ ConTrack مبني من الصفر (Next.js + Prisma)، فالبروتوكول نفسه
(A موجود / B امتداد / C جديد / D تكامل) يُطبَّق على **مديولات ConTrack** — والمرجع الودو
يخدم في الاتجاهين: **قائمة فحص وظيفية** (ماذا يغطي نظام ERP ناضج) و**انضباط القرار**
(لا تكرار لما بُني).

**الخطوات بالترتيب — توقف عند أول تطابق:**

| الخطوة | السؤال | القرار |
|---|---|---|
| 1 | هل المطلوب متغطي في ConTrack فعلاً؟ (افحص سجل المديولات §7 في مرجع Odoo + الشاشات الحالية) | **A = موجود** — استخدم الإعدادات/القوائم المرجعية، لا جدولاً جديداً |
| 2 | هل الكيان الأساسي (جدول/نموذج) موجود والمطلوب يضيف حقولاً/سلوكاً؟ | **B = امتداد** — حقول جديدة اختيارية + شاشات على النماذج الحالية |
| 3 | كيان جديد تماماً لا يقاربه شيء؟ | **C = مديول جديد** — يجب تبرير «لماذا لا يكفي الموجود» + قواعد §3 |
| 4 | يحتاج خدمة خارجية (دفع/توقيع/SMS/فاتورة إلكترونية)؟ | **D = تكامل** — ابحث عن الخدمة الجاهزة قبل البناء |

**قالب مخرجات القرار** (يُعبَّأ لكل طلب — كما في المرجع §1) — مع إزاحة الاسم:
`Models المتأثرة` = جداول Prisma المتأثرة، `المديول الأقرب` = وحدة ConTrack ذو صلة.

## 2) قواعد بناء أي مديول جديد/امتداد في ConTrack (المعدلة من §8 بالمرجع)

1. **هيكل ConTrack** بدل `__manifest__.py`: نموذج Prisma في `prisma/schema.prisma` + مسارات API في `src/app/api/**` + منطق نقي `src/lib/*-core.ts` + خادم `src/lib/*-server.ts` + واجهة `src/components/contrack/*`.
2. **التعدد الشركات إلزامي** (مقابل `company_id` في Odoo): كل جدول جديد يحمل `companyId Int @default(1) @map("company_id")` + `@@map` snake_case، ويُسجَّل في `TENANT_MODELS` (`src/lib/db.ts`) و`BACKUP_MODELS` (`src/lib/backup-dump.ts`) ويُراعى في purge (`api/data-mgmt`) — درس T111.
3. **لا enum في Prisma** — `String` بمفردات مقيدة في الكود (`CONTRACT_STATUSES`/`QUOTATION_STATUSES` نمطاً) + تعليق في السكيمة.
4. **الترقيم ذري** عبر `nextNumberByKey` (`number_sequences`) — لا `max+1` للجداول الحساسة.
5. **الصلاحيات**: مفتاح `screen_*` في `permissions-catalog.ts` + `VIEW_PERMS` (`nav-perms.ts`) + `perm` على بند الشل — حارس الاختبار `tests/nav-top-structure.test.ts` يفرض التغطية.
6. **البلاطة**: بند `NavModule` في `nav-structure.ts` + تون في `MODULE_TONE` (`AppShell.tsx`) + ملكية نشاط في `modules-catalog.ts` + فرع عرض في `ConTrackApp.tsx`.
7. **لا يُعدَّل النموذج المالي الموجود بشكل كسر** — الامتدادات تضيف حقولاً اختيارية بقيم افتراضية محايدة، والمنطق الحالي يظل متوافقاً مع مرجع NOVA (`contrack_v9.15.18` مُستبعد — المرجع `nova-reference/`).
8. **التدقيق**: `audit()` لكل تغيير حالة + جدول أحداث الكيان (`ContractEvent` نمطاً) + سند/قيود عبر المحركات القائمة (`voucher-server`) لا SQL مباشر — لا أرصدة رقمية مخزنة (اشتقاقية دائماً).

## 3) المطابقة — ما بُني في ConTrack مقابل خريطة Odoo

> التفصيل الكامل في سجل §7 بالمرجع المعتمد. الخلاصة: **12 مديولاً منفذاً** تغطي 8 من 11 مجالاً رئيسياً في Odoo.

| مجال Odoo | ConTrack | التغطية |
|---|---|---|
| Sales (`sale_management`) | **العقود وعروض الأسعار** (`qc`) | ✅ عرض ← عقد ← مراحل ودفعات + تحويل (b10a6e1) |
| Contacts + CRM | العملاء (`clients`) | ⚠️ جهات الاتصال مغطاة؛ **CRM (فرص بيع) غير موجود** |
| Accounting (`account`) | المحاسبة (`accounting`) | ✅ شبه كامل + زكاة/XBRL (ل10n الكويت جزئياً) |
| Purchase | الباطن (`subs`) جزئياً | ⚠️ عقود الباطن موجودة؛ **موردون + أوامر شراء عامة غير موجودة** |
| Inventory (`stock`) | المخازن (`warehouses`) | ✅ الأساس؛ امتدادات Odoo (باركود/تكاليف إضافية) غير موجودة |
| HR + Payroll | الموارد البشرية (`hr`) | ✅ التوظيف والتقييمات غير موجودين (أولوية منخفضة) |
| Project | المشاريع (`projects`) | ✅ + الاستشارات (`consulting` ≈ `hr_timesheet`) |
| POS | المبيعات (`sales`) | ✅ |
| Maintenance | الصيانة والتشغيل (`maintenance`) | ✅ |
| Documents/Sign/WhatsApp | مرفقات + مركز النماذج | ⚠️ DMS جزئي؛ **توقيع إلكتروني وواتساب/SMS غير موجودين (D)** |
| Portal | — | ❌ بوابة العميل غير موجودة |
| Website/eCommerce/Marketing | — | ❌ خارج نطاق نشاط المقاولات حالياً (لا يُخطط له) |

## 4) قائمة التطوير المرشحة — كل بند بقالب القرار

### ر1 — اكتمال مديول «العقود وعروض الأسعار» (المرحلة ب من `modules-arrangement.md`)

```
طلب: اكتمال دورة العرض ← العقد داخل الوحدة المستقلة qc
التصنيف: B امتداد (امتداد qc + نموذجي Quotation/Contract — لا جداول جديدة)
الجداول المتأثرة: quotations, quotation_items, contracts (+boq_items اختياريًا)
المبرر: التحويل الحالي (b10a6e1) يمرر العميل والاسم والقيمة فقط — بنود العرض
  لا تُرحَّل، والحالة نص أي→أي بلا مصفوفة، ومقبول بلا أثر جانبي، والترقيم
  يقرأ max بدلاً من العدّاد الذري (QUO مضروب في number_sequences ولا يُستخدم).
الحل المقترح (4 بنود مستقلة):
  1) ترحيل بنود العرض إلى العقد عند التحويل (QuotationItem → بنود BOQ/العقد)
     مع تتبع الأصل (نفس مبدأ نسخ BOQ المستقلة — نسخة لا مرجع).
  2) مصفوفة انتقالات العرض: جديد→مرسل→مقبول/مرفوض→منتهي (نمط
     lifecycle-transitions.ts) + قبول العرض يفتح معالج العقد جاهزًا (أثر الحالة).
  3) ترقيم العروض عبر nextNumberByKey("quotation:number","QUO",4).
  4) ربط العرض بمجموعة العقود (contractGroups) اختياريًا عند التحويل.
dependencies: [qc, lifecycle-transitions, number_sequences]
أثر على: صلاحيات: لا شيء | تقارير: الربط بالأصل يظهر في تقارير العروض |
  بيانات قائمة: لا ترحيل قسري — البنود القديمة تعمل كما هي.
مخاطر: الترحيل يضاعف بنود العقد إن كرره المستخدم → حرس التحويل المزدوج
  الموجود يمنعه (QUOTE_TO_CONTRACT_MARKER).
```

### ب — المشاريع الاستشارية كيان مستقل (قرار المالك 2026-11-16 «ب») — ✅ منفذ (b457d38)

```
طلب: مراجعة طبيعة مديول الاستشارات — المالك: «ليس للمقاولات بل نشاط منفصل» — ثم اعتماد الخيار ب
التصنيف: A إضافة مدارة (كيان جديد + تحويل هدف ثلاثة جداول HR) — الوثيقة: docs/consulting-projects-design.md
الجداول المتأثرة: +consulting_projects (CPR ذري) · engineer_assignments/engineer_timesheets/
  consulting_revisions ← هدف مزدوج (مشروع استشاري أو عقد — المراجعة هدفًا واحدًا والساعات والإسناد واحدًا على الأقل)
الحالة: ✅ منفذ ومتحقق حيًا (CPR-0001 + إسناد + ساعات + V1 على المشروع وV1 على العقد مع حدث العقد + حسم)
ملاحظة توافق: البيانات القديمة (المربوطة بعقد) تعمل كما هي — حدث العقد للمربوطة بعقد حصرًا.
```

### ر2 — ملف العميل الموحد (المرحلة ج من `modules-arrangement.md`)

```
طلب: بيانات العميل + عقوده + كشفه المالي + تعليقاته ومتابعته في مكان واحد
التصنيف: B امتداد (امتداد clients — كل الجداول موجودة)
الجداول المتأثرة: لا جداول جديدة — تجميع عرض (customers + contracts + vouchers + invoices + comments)
المبرر: البيانات كلها موجودة ومتفرقة بين شاشات؛ التجميع تطوير واجهة لا نماذج.
الحل المقترح: صفحة ملف العميل داخل clients تضم التبويبات (البيانات · العقود ·
  الكشف المالي · التعليقات والمتابعة) — نمط ContractDetailView الصفحي القائم.
dependencies: [clients]
أثر على: لا صلاحيات جديدة (تجميع بشاشات مفتوحة سلفًا).
مخاطر: لا شيء مادي — شاشة قراءة وتجميع.
```
الحالة: ✅ منفذ ومتحقق حيًا (الجلسة 17 — أربع تبويبات في CustomerFilePage + كشف شامل مضمّن مع PDF
+ مهام متابعة بالعميل + نقل التعليقات لتبويبها + إصلاح الكشف الشامل في شاشة الكشوفات الذي كان
يقرأ بنية sections قديمة لا يرسلها الخادم)

### ر3 — فرص البيع (CRM خفيف) — ✅ منفذ ومتحقق حيًا (اعتماد المالك «كليهما معًا»)

> الوثيقة: `docs/opportunities-design.md` — اعتُمدت (د1–د7 بالافتراضات) ونُفّذت.

```
طلب: تتبع الفرص قبل عرض السعر (خط أنابيب: فرصة ← مؤهَّلة ← عرض)
التصنيف: C جديد (لا كيان «فرصة» في ConTrack، والعميل قد لا يكون موجودًا بعد)
الجداول الجديدة المقترحة: opportunities (companyId, name, customerId?, stage,
  expectedAmount, expectedCloseDate, source, quotationId?, notes) — يتكامل مع
  qc لاحقًا (فرصة ← عرض سعر).
المبرر: المرجع يفصل CRM عن المبيعات؛ غياب مرحلة ما قبل التسعير يعني فقدان
  الفرص التي لم تصل مرحلة العرض. البديل الأرخص: عمود «المصدر» في العروض — لكنه
  لا يلتقط الفرص المرفوضة قبل التسعير.
dependencies: [customers, qc]
أثر على: مديول/بلاطة جديدة (ملكية نشاط المقاولات) + صلاحية screen_opportunities.
مخاطر: الحمل الإداري على المستخدمين إن أُجبروا على تسجيل الفرص — الحل: اختياري
  غير مفعّل افتراضيًا (feature flag).
```

الحالة: ✅ منفذ ومتحقق حيًا — OPP ذري (nextNumberByKey) + مراحل مغلقة تُعرض قائمة الانتقالات
المسموحة حصرًا + إصدار عرض من الفرصة يفتح معالج العروض معبأً ويربط ويرفع المرحلة داخل معاملة الإصدار،
وقبول/رفض العرض في transition يزامن الفرصة آليًا (مقبولة/مفقودة بسبب افتراضي قابل للتعديل) + زر
«إنشاء عميل من الفرصة» + مؤشرات اشتقاقية — التفعيل يدوي من الإعدادات (لا اقتراح آلي من Onboarding).

### ر4 — الموردون وأوامر الشراء — ✅ منفذ ومتحقق حيًا (اعتماد المالك «كليهما معًا»)

> الوثيقة: `docs/purchase-design.md` — اعتُمدت (د1–د9 بالافتراضات) ونُفّذت.

```
طلب: شراء مواد للعقود (طلب ← أمر شراء ← إذن إدخال ← سند صرف/دفعة مورد)
التصنيف: B امتداد لمديول المخازن (+ جدول suppliers وأوامر شراء جديدان C جزئي)
الجداول: suppliers (جديد) + purchase_orders + purchase_order_items (جديد)؛
  الإدخال يمر عبر stock_docs الموجودة؛ الدفع عبر سندات الصرف الموجودة.
المبرر: المخازن تغطي حركة الأصناف لا مسار الشراء بموافقاته؛ المرجع يفصل
  `purchase` عن `stock`. الباطن يغطي تعاقد أعمال لا شراء مواد.
dependencies: [warehouses, accounting/vouchers, subs للربط بالعقد]
أثر على: بلاطتان متأثرتان (مخازن/محاسبة) + صلاحية جديدة + تقارير مشتريات.
مخاطر: تكرار جزئي مع أذون المخازن الحالية → التصميم يبدأ من إذن الإدخال
  المرتبط بأمر شراء لا من جدول موازٍ.
```

الحالة: ✅ منفذ ومتحقق حيًا — SUP/PO ذريان + آلة حالات مغلقة (مسودة→مرسل للمورد→جزئي→مستلم/ملغى)،
والاستلام يستدعي createStockDocTx القائمة داخل المعاملة نفسها (لقطة سعر الأمر للمتوسط المرجحي وقيد
مدين 1160/دائن 2111 باسم المورد) بلا تجاوز للمطلوب برسالة بالأرقام، وPDF خادمي للأمر، وسند صرف مورد
PV عبر محرك السندات (partyType=supplier + supplierId)، وStockDoc.purchaseOrderId + Voucher.supplierId
عمودان اختياريان — تسجيلات TENANT/BACKUP/الكتالوج/التنقل/الصلاحيات كاملة.

### ر5 — بوابة العميل — مرشح بعيد المدى

```
طلب: العميل يرى عقوده ودفعاته المستحقة وكشوفه دون دخول النظام
التصنيف: C جديد (رابط خارجي مؤقت برمز آمن — لا حسابات كاملة أولًا)
الجداول: لا جداول جديدة تقريبًا (رموز وصول مؤقتة customer_portal_tokens)
المبرر: Odoo يفصل `portal`؛ القيمة علاقة عامة + تقليل مكالمات السؤال عن المستحقات.
dependencies: [customers, contracts, payment_plan, statements]
أثر على: مسار عام جديد (خارج الحرس الحالي) — أمان أولًا: رموز هاشة + صلاحية قراءة فقط.
مخاطر: أعلى مخاطرة أمنية في القائمة → يُنفَّذ بمرحلتين (رابط كشف PDF مؤقت أولًا).
```

الحالة: ✅ **منفذ ومتحقق حيًا — المرحلة أ** (`8eefcbb` البطاقة → التنفيذ): جدول `customer_portal_tokens`
(هاش SHA-256 حصرًا — الصريح مرة واحدة حواريًا) + صلاحية 30/90/365 بمقارنة خادمية بلا cron + إبطال فوري
من تبويب «الكشف المالي» بملف العميل + مسار عام `GET /api/portal/statement/[token]` بلا authGuard برفض
عام موحد 404 + نفس كشف ر2 PDF حرفيًا عبر `forCompany` من صف الرمز + حد طلبات نافذة بالذاكرة (نقية
باختبارات — dev يعيد بناء الوحدة لكل طلب والإنتاج يحفظها بين الطلبات) + lastUsedAt/Ip بلا عدادات
(G9) + TENANT/BACKUP + audit — تحقق حي: إنشاء من الواجهة → عرض مرة واحدة → PDF بلا تسجيل دخول
(200 application/pdf) → إبطال → 404 عام → شارات نشط/مبطول بآخر استخدام وIP → جوال 390.
المرحلة ب (صفحة بوابة عامة بمؤشرات ودفعات مستحقة): بأمر المالك حصرًا — §7 البطاقة.

### ر6 — تكاملات خارجية (D) — حسب الحاجة لا الاستباق

| التكامل | مكافئ Odoo | الحالة | القرار |
|---|---|---|---|

| فاتورة إلكترونية كويتية | `l10n_kw_edi` (لم تصدر) | الزكاة/XBRL منفذة | D — عند صدور التنظيم حصريًا |
| بوابة الدفع | `payment` | ✅ منفذة (`api/gateway/*`) | A موجود |

## 5) التسلسل المقترح (بانتظار اعتماد الأولوية من المالك)

1. **ر1 — اكتمال qc** (أقرب وأرخص: امتداد بلا جداول جديدة، يكمل قرار الفصل المعتمد).
2. **ر2 — ملف العميل الموحد** (تجميع واجهة، بلا نماذج).
3. **ر3 أو ر4** حسب أولوية المالك (فرص بيع قبل شراء مواد أم العكس) — كلاهما يحتاج تصميمًا تفصيليًا وورقة قراءة قبل الكود.
4. **ر5/ر6** متى طلبت الحاجة. — ✅ **ر5 المرحلة أ منفذة ومغلقة** (الجلسات 21+22 — البطاقة docs/customer-portal-design.md) والمرحلة ب بأمر المالك حصرًا (§7).

كل بند يُسلَّم: ورقة تصميم ← اعتماد المالك ← تنفيذ ← lint + اختبارات + تحقق متصفحي ← commit ← نشر ← تحقق حي (قواعد PROJECT-LOG §7).

## 6) القرارات المطلوبة من المالك

- **س1 — اعتماد البروتوكول**: هل يُعتمد بروتوكول القرار (§1) + قواعد الإنشاء (§2) **إلزامية** لكل مديول قادم (تُذكر في كل ورقة تصميم)؟ اقتراحي: نعم، مع القالب المعبأ في كل ورقة.
- **س2 — أولوية القائمة**: أي البنود نبدأ به؟ اقتراحي: **ر1 ثم ر2** (إتمام الفصل المعتمد قبل فتح مديولات جديدة).
- **س3 — بند ر1/1 الترحيل**: عند تحويل عرض إلى عقد، هل تُرحَّل بنود العرض إلى بنود العقد (BOQ) **افتراضيًا** مع إمكانية إلغاء الاختيار، أم تبقى إضافة يدوية بعد الإنشاء؟
