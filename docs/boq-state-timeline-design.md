# تصميم «خط زمن حالة BOQ» — السابق/الحالي · الاعتماد · السقوط · الاسترجاع الزمني (as-of)

> **المصدر:** فكرة المالك عقب استيراد BOQ الحقيقي (الجلسة 4): «موضوع السابق والحالي… لا بد أن يكون فيه اعتماد بأنه تم عمل الحالي وأصبح **ساقًا**؛ لما أفتح BOQ في أي تاريخ قبل الاعتماد يجيب الحالة التي كان عليها».
> وهي بعينها أعمدة G–J في ملف المالك الحقيقي (`PERVIOUS | CURRENT | Total percentage | Total Price` — boq-import-design §1.2) التي أُهملت بقرار v1 (§2.5.2) — هذه الدراسة هي التفعيل الكامل لدلالتها.
> **الغرض:** ترجمة الفكرة إلى معمارية فوق النماذج القائمة حصرًا (تطوير لا بناء جديد — قرار nova-code-review §6).

---

## 0) ما تقوله الفكرة — الترجمة المفاهيمية

| مصطلح المالك | معناه في النظام |
|---|---|
| **السابق** | التراكمي المعتمد لكل بند: Σ كميات أسطر المستخلصات **المعتمدة** |
| **الحالي** | كميات مسودة المستخلص **قيد الإعداد** (لم تُعتمد بعد) |
| **الاعتماد** | الحدث الذي يجمّد المستخلص (لقطات تراكمية) ويحوّل «حاليه» إلى «سابق» |
| **أصبح ساقًا** | كل حالة أغلقها اعتمادٌ أحدث = **مغلقة نهائيًا لا تُعدَّل** — تُقرأ بالتاريخ فقط |
| **أفتح BOQ في أي تاريخ** | إعادة بناء الحالة الكاملة كما كانت لحظة ذلك التاريخ: بنية البنود (قبل/بعد الملاحق) + سابق/حالي/نسبة كل بند |

**لماذا «مكان لم يفكر فيه أحد»:** الأنظمة المحاسبية تخزن الحالة الراهنة وتدفن التاريخ في أرشيف لا يُستجوب. بمعمارية G9 (كل العدادات مشتقة من صفوف مؤرخة — field-execution-design §0) **التاريخ محفوظ في نظامنا أصلًا بلا كلفة إضافية**؛ الناقص ثلاثة أشياء فقط: لحظة اعتماد رسمية للمستخلص، محرك استرجاع زمني، وواجهة زمنية. أي أن «الآلة الزمنية» تُبنى فوق وقود موجود.

## 1) مصادر الأحداث — كلها قائمة، لا جداول جديدة

| الحدث | المصدر القائم | أثره على حالة BOQ |
|---|---|---|
| استيراد BOQ | `BoqItem.itemNo/divisionCode/divisionName` (الجلسة 4) | بنية البنود الأولية |
| اعتماد ملحق | `Addendum.status=معتمد` + `approvedDate` + `AddendumItem` (add/delete) | إضافة/حذف بنود **بتاريخ الاعتماد** |
| فتح مسودة مستخلص | `Invoice` + `InvoiceItem` (بالربط الجديد §2) | «الحالي» يبدأ الامتلاء |
| اعتماد مستخلص | (الجديد §3) `Invoice.state` + `approveAt` + لقطات `cumulativeQty` | «الحالي» يُجمَّد وينضم إلى «السابق» |
| إلغاء فاتورة | `Invoice.status=void` + `voidReason` | تُستبعد من كل الاشتقاقات |
| تنفيذ ميداني | `FieldExecution` | **لا يمس الرسمي إطلاقًا** — طبقة التنبؤ (docs/daily-report-forecast-design.md) |

## 2) الفجوة الأولى — سطر المستخلص بلا بند

عداد «مفوتر» محصور اليوم على مستوى العقد (حد موثق في field-execution-design §1: «الربط بالبند لاحق»). هذه الدراسة تسدّه:

| الإضافة على `InvoiceItem` | الدلالة |
|---|---|
| `boqItemId Int?` → `BoqItem` | السطر يخص بند BOQ محددًا (الفارغ يبقى سطرًا حرًا — توافق خلفي كامل) |
| `cumulativeQty Decimal @default(0)` | **لقطة الاعتماد**: تراكمي البند لحظة الاعتماد — مرآة حرفية لـ `SubCertificateLine.cumulativeQty` (retention-design §3.2) |

- واجهة الفاتورة: عند اختيار عقد، سطر البند يختار من بنود BOQ للعقد (برقم البند وشارة القسم من استيراد الجلسة 4) — الوحدة والسعر يُملآن منه.
- **حارس المتاح** (مرآة SubIPC §3.4): Σ كميات الأسطر على البند في المسودة ≤ كمية البند − Σ المعتمد السابق؛ التجاوز يُرفض برسالة صريحة.

## 3) الفجوة الثانية — آلة اعتماد مستخلص العميل

`Invoice.status` الحالي مالي صرف (unpaid|partial|paid|void) — **دورة الاعتماد الهندسية بُعد متعامد جديد**:

```
state:  مسودة ──تقديم──▶ مقدم ──اعتماد──▶ معتمد ──(سداد القائم)──▶ مدفوع (status القائم كما هو)
           │               │                │
           └───────────────┴────────────────┴──▶ ملغي (status=void القائم — بسبب)
```

| القرار | المضمون |
|---|---|
| `state String @default("معتمد")` + `submitBy/submitAt` + `approveBy/approveAt` | **كل المسارات القائمة لا تتغير حرفيًا** — الإنشاء الافتراضي معتمد ينشر قيده فورًا كما اليوم؛ المسودة خيار صريح جديد |
| المسودة بلا قيد | نشر قيد الإصدار (بأسطر المحتجزات الثلاثة — retention §1.2) ينتقل إلى لحظة الاعتماد، مع تحقق الفترة المفتوحة وقتها |
| تعديل الأسطر/الحذف: **مسودة حصرًا** | مرآة قاعدة SubIPC G7 |
| **المعتمد لا يُعدَّل** | «الاعتماد لحظة الحقيقة» (retention §3.4) — أي تصحيح بمستخلص لاحق. هذا هو **السقوط**: ما اعْتُمد لا يعود قابلاً للتحرير أبدًا، ويُسترجع بوضعه التاريخي فقط |
| الروابط والسداد | لا روابط سداد ولا إفراج محتجزات ولا تخصيص FIFO إلا على `state=معتمد` |

## 4) محرك الحالة الزمنية — `src/lib/boq-state-core.ts` (نواة نقية بلا db — نمط parse-core)

```
deriveBoqState({ asOf, items, addenda, invoices, lines })
  → { items: [{
      بند ظاهر؟ · تعاقدي (as-of) · سابق · حالي · نسبة كلية · متاح · قيمة سابقة/حالية
    }], إجماليات القسم/العقد }
```

- **بنية as-of**: بند يظهر ⟺ ليس محذوفًا بملحق **معتمد** `approvedDate ≤ asOf` (الحذف الناعم `deletedAddendumId` يُفكّ إلى تاريخ اعتماد ملحقه)؛ والمضاف بملحق معتمد ≤ asOf يدخل.
- **سابق** = Σ `cumulativeQty`/كميات أسطر فواتير `state=معتمد` و`approveAt ≤ asOf` (الملغاة مستبعدة).
- **حالي** = Σ كميات أسطر المسودات/المقدم المنشأة ≤ asOf.
- **نسبة كلية** = (سابق+حالي) ÷ تعاقدي — قد تتجاوز 100% (تنفيذ زائد — إشارة حقيقية لا تُخفى، نمط field-execution §4).
- الأعمدة الناتجة **مرآة أعمدة الملف الأصلي G–J حرفيًا** — من يقرأ مستخلص الاستشاري يقرأ شاشتنا بلا ترجمة.

## 5) المسارات والواجهة

| المسار | الدور |
|---|---|
| `GET /api/contracts/[id]/boq/state?asOf=YYYY-MM-DD` | الحالة الكاملة (افتراض: الآن) — حرس `screen_contracts` |
| `GET /api/contracts/[id]/boq/timeline` | الأحداث المؤرخة: استيراد · ملاحق معتمدة · مستخلصات (فتح/تقديم/اعتماد/إلغاء) — وقود شريط الزمن |
| `POST /api/invoices/[id]/submit` · `/approve` | آلة الحالة (approve يجمّد اللقطات وينشر القيد داخل معاملة) |

**الواجهة (قسم «بنود الكميات»):**
- عمودان جديدان **«سابق/حالي»** + النسبة — للعقود ذات مستخلصات مرتبطة بالبنود.
- **شريط زمني أفقي** أعلى الجدول: نقطة لكل حدث (أيقونة+تاريخ)، الضغط يقفز بالعرض إلى حالته.
- منتقي **«افتح كما كان في…»** (تاريخ) — الوضع التاريخي: قراءة فقط، شارة «📂 وضع تاريخي»، وشارة **«ساق»** على كل مستخلص أغلقته اعتمادات أحدث.
- الجوال: بطاقة البند تعرض سابق/حالي/نسبة، والشريط الزمني قائمة منسدلة.

## 6) خطة التنفيذ — كل مرحلة مستقلة قابلة للاختبار (الأساس 1016/1016)

| المرحلة | النطاق | الاختبار |
|---|---|---|
| **ز1** | `InvoiceItem.boqItemId + cumulativeQty` + منتقي البند في الفاتورة + حارس المتاح + إكمال عداد «مفوتر بالبند» في المقايسة (takeoff) | نواة + مسار |
| **ز2** | آلة `state` (مسودة/مقدم/معتمد) + انتقال نشر القيد إلى الاعتماد + تجميد اللقطات + حراسة الروابط | نواة + مسار + قيد |
| **ز3** | `boq-state-core` + `state`/`timeline` + الواجهة (أعمدة + شريط زمني + as-of + شارات) | نواة + واجهة |

كل مرحلة: `bun test` أخضر + lint نظيف + تحقق حي بالمتصفح (دورة: مسودة → اعتماد → فتح BOQ بتاريخ سابق → مطابقة الحالة).

## 7) حدود v1 (معلنة)

1. **as-of بالتاريخ الفعلي (valid-time)** — لا تدقيق «زمن المعاملة» الكامل (bitemporal)؛ يكفي غرض الاعتماد الهندسي والمالي.
2. **«الحالي» (المسودات) يُبنى من قيمها الراهنة** — لا تاريخ تحرير لأسطر المسودة؛ أما «السابق» فمقطوع باللقطات (`cumulativeQty`) فدقته مطلقة.
3. **الاستيراد يبقى إلحاقيًا** (قرار الجلسة 4 §2.5.6) — «نسخة BOQ معدّلة» تُدار بأداة الملحق القائمة (add/delete بتاريخ اعتماد)؛ ترقية مستقبلية معلنة: استيراد كنسخة جديدة بقفل مؤرخ عند الاعتماد.
4. **لا تعديل رجعي للمُعتمد إطلاقًا** — السقوط جوهري الفكرة: بدونه يفقد الاسترجاع الزمني معناه.
